﻿﻿# 异常处理

程序出错不可怕，出错后行为可控才重要。这一篇讲异常机制、正确的捕获粒度、自定义异常体系，以及finally和资源清理。

## 异常是什么

程序运行出错时，Python抛出（raise）异常对象；没人处理它，程序就带着栈回溯终止：

```python
print(1 / 0)
# Traceback (most recent call last):
#   File "main.py", line 1, in <module>
# ZeroDivisionError: division by zero
```

学会读Traceback：**从下往上看**。最后一行是异常类型和消息（ZeroDivisionError），往上依次是调用栈，最底下的是最初触发点。定位bug先看最后一行，再顺着栈找自己代码的文件行号。

常见内置异常速查：

| 异常                  | 触发场景                     |
| --------------------- | ---------------------------- |
| ValueError            | 类型对但值不对：int("abc") |
| TypeError             | 类型不对："a" + 1          |
| KeyError / IndexError | 字典键 / 序列下标不存在      |
| FileNotFoundError     | 文件不存在                   |
| AttributeError        | 对象没有该属性               |
| ZeroDivisionError     | 除零                         |
| ConnectionError       | 网络连接问题                 |
| ImportError           | 模块导入失败                 |

## try/except：捕获与处理

```python
try:
    n = int(input("输入数字："))
    print(100 / n)
except ValueError:
    print("请输入合法数字")
except ZeroDivisionError:
    print("不能除以零")
```

执行流程：try块正常跑完 → 跳过所有except；try块某行抛异常 → 立即中断，从上到下找第一个匹配的except执行。

### 捕获多个异常与异常对象

```python
try:
    risky()
except (ValueError, TypeError) as e:    # 元组写法捕获多种
    print(f"参数问题: {e}")
except Exception as e:                   # 兜底print(f"未知错误: {e}")
```

### 捕获粒度：最重要的工程判断

反面教材：

```python
try:
    process_order(order)          # 一大段业务
    except Exception:                 # 裸捕获，吞掉一切
        pass                          # 什么都不做——bug从此隐身
```

问题：所有异常（包括拼写错的变量名NameError、程序员失误）全被吞掉，程序表面正常、数据悄悄损坏，排查时无线索。

正确姿势三层：

```python
# 1. 捕获具体异常，处理你预见到的try:
    data = json.loads(raw)
except json.JSONDecodeError as e:
    logger.warning("非JSON输入: %s", e)
    return None

# 2. 顶层兜底要记日志try:
    run()
except Exception:
    logger.exception("未处理异常")    # exception() 自动带栈回溯
    raise                              # 记了日志再抛出去，别吞

# 3. 预料之外的就让它崩（fail fast），比带病运行好
```

判断标准：**这个异常我能做什么有意义的事吗？** 能（换默认值、重试、返回错误码）就捕获处理；不能就放它走，让上层或全局处理器接手。

### else与finally

```python
try:
    data = json.loads(raw)
except json.JSONDecodeError:
    print("解析失败")
else:
    # 没抛异常才执行：把"成功路径"和"错误处理"分开
    print("解析成功", data["id"])
finally:
    # 无论成功失败都执行：清理资源print("清理连接")
```

finally不看结果必定执行，即使try里有return（return的值先算好，finally跑完才真正返回）。

## 主动抛异常：raise

```python
def set_age(age: int):
    if not isinstance(age, int):
        raise TypeError(f"age必须是int，收到 {type(age).__name__}")
    if not 0 <= age <= 150:
        raise ValueError(f"age超出合理范围: {age}")
    ...

set_age(-5)    # ValueError: age超出合理范围: -5
```

错误输入"抛异常让它崩"好过"返回 -1混过去"：异常带类型和消息，调用方无法忽略；魔法返回值必然被遗忘处理。

### 3.1异常链：raise ... from ...

捕获底层异常后抛出更贴业务的上层异常，用from保留因果：

```python
class ConfigError(Exception):
    """配置加载失败。"""

def load_config(path: str) -> dict:
    try:
        with open(path, encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError as e:
        raise ConfigError(f"配置文件不存在: {path}") from e
    except json.JSONDecodeError as e:
        raise ConfigError(f"配置文件不是合法JSON: {path}") from e
```

输出的Traceback会有两段：

```
The above exception was the direct cause of the following exception:
Traceback ...
ConfigError: 配置文件不存在: config.json
```

底层原因（哪个文件、什么错）完整保留，排查时不用猜。抛新异常不写from，Python也会隐式链接（During handling of the above exception...），但显式from语义更清楚：from e表示"由它引起"。

### 异常里带数据

异常是对象，可以携带结构化信息：

```python
class ApiError(Exception):
    def __init__(self, status: int, message: str):
        self.status = status
        self.message = message
        super().__init__(f"[{status}] {message}")

try:
    raise ApiError(404, "用户不存在")
except ApiError as e:
    print(e.status, e.message)      # 404用户不存在，可以按status决定重试还是报错
```

## 自定义异常体系

项目异常按模块分级，调用方可以精确捕获也可以一把兜住：

```python
# exceptions.py
class AppError(Exception):
    """项目所有异常的基类。"""

class DatabaseError(AppError): ...
class ExternalApiError(AppError):
    def __init__(self, service: str, status: int):
        self.service, self.status = service, status
        super().__init__(f"{service} 返回 {status}")

class OrderNotFoundError(AppError):
    def __init__(self, order_id: str):
        self.order_id = order_id
        super().__init__(f"订单不存在: {order_id}")

# main.py
try:
    ...
except OrderNotFoundError as e:      # 精确处理
    return {"code": 404, "msg": str(e)}
except AppError as e:                # 业务兜底
    return {"code": 500, "msg": str(e)}
```

设计原则：基类继承Exception；异常名以Error结尾；消息面向开发者（日志可读），用户展示文案由上层翻译。

## EAFP风格：

Python的哲学Python社区推崇EAFP（Easier to Ask Forgiveness than Permission，先干再说，错了处理），而不是LBYL（Look Before You Leap，先检查再干）：

```python
# LBYL：先判断
if "key" in d and os.path.exists(path):
    value = d["key"]

# EAFP：直接干try:
    value = d["key"]
except KeyError:
    ...
```

EAFP通常更快（无竞态：判断和操作之间状态不会变）且更清晰。但注意别用try/except压制正常逻辑——正常情况下几乎不失败的路径用if更直白。

## 资源清理的完整姿势with是首选（见第11篇上下文管理器）。需要手动管理时：

```python
conn = connect()
try:
    conn.query(sql)
finally:
    conn.close()      # 无论成败都关闭
```

finally里再抛异常会覆盖原异常——finally里只做不会失败的清理（close用try包住或忽略错误）。

## 常见坑

1. **except Exception: pass**：bug隐身术。哪怕要吞也要log。

2. **捕获范围过宽**：except: 连KeyboardInterrupt（Ctrl+C）、SystemExit都捕获，程序都停不下来。至少写except Exception:。
3. **在except里return掩盖问题**：接口层返回500是对的，业务层默默return None是灾难。
4. **finally里return**：会覆盖try里的返回值，诡异行为，禁止。
5. **用异常做流程控制**：循环里靠捕获IndexError停止，正常做法是len判断或迭代器。异常的创建和栈回溯有成本，热路径滥用会拖慢程序。
6. **丢失原始异常**：except A as e: raise B(...) 不写from e，栈回溯会令人困惑。重抛用raise（空raise原样再抛）或raise B() from e。
7. **日志用f-string拼接**：logger.error(f"fail {e}") 在日志被禁用时也执行拼接。延迟格式化：logger.error("fail %s", e)。
