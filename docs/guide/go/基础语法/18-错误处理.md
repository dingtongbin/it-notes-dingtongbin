# 错误处理

Go 没有异常，错误是普通值。if err != nil 是 Go 代码的主体节奏。这一篇讲清 error 的本质、三条纪律和标准库工具。

## error 的本质：一个接口

```go
type error interface {
	Error() string
}
```

任何实现了 Error() string 的类型都是 error。常见创建方式：

```go
import (
	"errors"
	"fmt"
)

err1 := errors.New("file not found")             // 静态错误
err2 := fmt.Errorf("invalid port: %d", port)     // 格式化错误
err3 := fmt.Errorf("connect %s: %w", host, err)  // %w 包装底层错误
```

## 标准处理节奏

```go
func loadConfig(path string) (*Config, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, fmt.Errorf("read config %q: %w", path, err)   // 包装后上抛
	}
	var cfg Config
	if err := json.Unmarshal(data, &cfg); err != nil {
		return nil, fmt.Errorf("parse config: %w", err)
	}
	return &cfg, nil
}

// 调用方
cfg, err := loadConfig("app.json")
if err != nil {
	log.Fatalf("启动失败: %v", err)      // 顶层打日志
}
```

三条纪律：

第一，立即处理或立即上抛，绝不吞掉错误。

第二，上抛时加上下文，用 %w 一路包装，错误信息自带调用链。

第三，只在顶层打日志。每层都 log 会重复刷屏，中间层只包装。

## panic 与 error 的边界

判断口诀：调用方"能做点什么"就用 error；做什么都没用、代码写错了才 panic。

```go
// panic：程序级 bug（数组越界、nil 解引用）或不可恢复的初始化失败
// error：预期的失败路径（文件不存在、网络超时、参数非法）
```

库代码绝不 panic，把决定权交给调用方；main 或初始化阶段可以 log.Fatal。panic 与 recover 机制单独一篇讲。

## 工程模式

模式一，在 defer 里包装错误，用命名返回值：

```go
func process(path string) (err error) {
	f, err := os.Open(path)
	if err != nil {
		return fmt.Errorf("open: %w", err)
	}
	defer func() {
		if cerr := f.Close(); cerr != nil {
			err = fmt.Errorf("close: %w", cerr)      // 关闭失败也不丢
		}
	}()
	return nil
}
```

模式二，循环里收集多个错误再合并，Go 1.20+ 用 errors.Join：

```go
var errs []error
for _, u := range urls {
	if err := check(u); err != nil {
		errs = append(errs, fmt.Errorf("%s: %w", u, err))
	}
}
return errors.Join(errs...)          // 全成功时返回 nil
```

## 常见坑

第一个坑：用 == 比较错误。错误一旦被包装，== 比较就失效，要用 errors.Is、errors.As（下一篇详细讲）。

第二个坑：fmt.Errorf 用 %v 会包信息但断了 errors.Is 的链，要被识别必须用 %w。

第三个坑：吞错误如 _ = err，或 if err != nil { return nil } 悄悄丢掉，golangci-lint 的 errcheck 能抓。

第四个坑：错误信息大写开头或带句号，Go 风格是小写开头无标点，方便日志拼接。
