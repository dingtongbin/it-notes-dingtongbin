# 接口

Go 的接口和 Python、Java 都不同：隐式实现，方法集决定匹配，小接口为王。这是 Go 设计哲学的核心。这一篇讲透。

## 隐式实现

定义接口，只要类型"有这样的方法"就算实现，不需要任何 implements 声明：

```go
// 定义接口：方法签名集合
type Storage interface {
	Save(key string, data []byte) error
	Load(key string) ([]byte, error)
}

// 实现：只要"有这些方法"就算实现
type MemoryStorage struct {
	data map[string][]byte
}

func (m *MemoryStorage) Save(key string, data []byte) error {
	m.data[key] = data
	return nil
}

func (m *MemoryStorage) Load(key string) ([]byte, error) {
	if v, ok := m.data[key]; ok {
		return v, nil
	}
	return nil, fmt.Errorf("key %q not found", key)
}

// 直接就能当 Storage 用
var s Storage = &MemoryStorage{data: make(map[string][]byte)}
```

价值在于解耦不经过"注册"：你可以给第三方库的类型补接口实现，对方完全无感知。Python 靠鸭子类型运行时判断，Go 在编译期静态判断加鸭子语义。

## 小接口：先想消费方

标准库的地基 io.Reader 只有一个方法，最大公约数：

```go
type Reader interface {
	Read(p []byte) (n int, err error)
}
```

组合成大接口：

```go
type ReadWriteCloser interface {
	Reader
	Writer
	Closer
}
```

Go 的传统是"接口定义在消费方"：调用代码需要什么能力就定义什么接口，而不是实现方提供大而全的接口。这颠覆了 Java 时代的习惯：

```go
// 消费方（service）自己定义需要的最小接口
type OrderRepo interface {
	FindByID(id int) (*Order, error)
	Save(o *Order) error
}

type OrderService struct {
	repo OrderRepo
}
```

这样 service 只依赖最小接口，测试时 mock 也只实现这两个方法即可。

## 标准库里的小接口实战

用 io.Reader 做通用处理，文件、网络、内存、压缩流都能满足：

```go
func process(r io.Reader) error {
	data, err := io.ReadAll(r)
	_ = data
	return err
}

process(file)
process(conn)
process(bytes.NewReader([]byte("hi")))
process(gzip.NewReader(file))
```

fmt.Stringer 控制打印形态，对标 Python 的 __str__。String 方法在上面 iota 篇讲过：

```go
type Order struct{ ID int; Title string }

func (o Order) String() string {
	return fmt.Sprintf("#%d %s", o.ID, o.Title)
}
fmt.Println(order)                 // 自动调 String()
```

## 设计纪律

接口定义在消费方，不要先造接口再想谁实现；接口方法超过 3 个要警惕职责过多，拆分。Go 谚语：接口越大，抽象越弱。

## 常见坑

第一个坑：值接收者与指针接收者的方法集不同。var s Storage = MemoryStorage{}（值）只在方法全为值接收者时成立，有指针接收者方法就必须 &MemoryStorage{}。

第二个坑：接口方法太多说明职责过重，改成小接口组合。

第三个坑：接口嵌入成环，A 嵌 B、B 嵌 A 编译错。
