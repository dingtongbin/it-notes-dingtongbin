# 基准测试与覆盖率

测试证明正确性，基准测试回答"快不快"，覆盖率回答"测到没（多少比例）"。两个都是 go test 官方能力，零额外工具。这一篇讲怎么写基准测试、怎么看覆盖率、以及怎么筛测试、跑并行。

## Benchmark：给函数计时

基准测试函数以 Benchmark 开头、参数是 testing.B，里面循环体是 b.N：

```go
// calc_test.go
func BenchmarkAdd(b *testing.B) {
	for i := 0; i < b.N; i++ {
		_ = Add(i, i)
	}
}
```

跑基准：

```bash
go test -bench . -benchmem
```

-bench . 表示跑当前包所有基准（可以给正则筛子），-benchmem 额外输出每次分配了多少内存。

## b.N 的循环是什么意思

b.N 不是你要写死的次数，而是框架自动调整：它会先跑小样本测出耗时，再放大 b.N 到能让测试稳定统计的量级。所以基准函数要把被测代码放在 b.N 的循环里，框架来决定循环多少次。

## 结果的读法

一次基准输出类似：

```
BenchmarkAdd-8  100000000  1.5 ns/op  0 B/op  0 allocs/op
```

-100000000 是 b.N，1.5 ns/op 是每次耗时，后面是每次内存分配。耗时和分配是最关注的两列。优化时就是盯这两个数在变好还是变差。

## 预热与计时精度

基准里有些代码（如初始化、数据准备）不该算进被测计时。用三种方式控制：

```go
b.ResetTimer()        // 重置计时起点
b.StopTimer()         // 暂停
b.StartTimer()        // 恢复
```

典型写法：先做准备，再 ResetTimer 清零，再进 b.N 循环。这样准备不被计入。

## 基准的对比意义

单跑一次基准绝对值参考意义有限，基准真正有用是做对比：改完代码 A/B 各测一次，看 ns/op 是升还是降。配合 -benchmem 观察内存分配，能发现意外的新分配。

## 覆盖率：测到多少

```bash
go test -cover ./...          # 看每个包/总体的覆盖率
go test -coverprofile=cover.out ./...   # 把覆盖率写进文件
go tool cover -html=cover.out  # 用浏览器可视化看每行覆盖
```

覆盖率告诉你"测了多少"，不是"质量"本身。100% 覆盖也能漏逻辑分支，但覆盖率低通常意味着大面积没测，是一个粗糙但有效的地基指标。

## 筛选与并行

```bash
go test -run TestAdd ./...              # 只看单个测试
go test -run TestAdd -count=1           # 禁用缓存，确保真的跑了
go test -race ./...                     # 开竞态检测（并发测试必加）
```

并发相关的测试记得配 -race 跑，前面竞态篇也提到过。测试进 CI 时，缓存和只跑子集这两个教训能避免很多假通过。

## 常见坑

1. 基准函数里把要测的代码写在 b.N 外层：等于没测。
2. 忘预热就 ResetTimer：准备耗时要扣掉。
3. 只看覆盖率不看逻辑：覆盖率是底线，别把它当目标。
4. 并发测试不加 -race：竞态可能不触发不报告。

## 小结

Benchmark 证明性能、coverage 给出覆盖面、-run/筛选和 -race 让测试可控可靠。这三类都是 go test 自带能力，会写会跑，性能回退和并发 bug 能更早被拦住。
