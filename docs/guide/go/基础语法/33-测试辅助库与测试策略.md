# 测试辅助库与测试策略

前两篇讲完了 testing 的标准骨架，但真实项目里纯手写 if，断言会很啰嗦，接口依赖也不好隔离。这一篇把测试往工程化推一步：用断言库减少样板、用接口 mock 截掉外部依赖、用边界覆盖补齐漏洞。侧重点是策略，不是堆语法。

## 断言辅助库 testify

标准库的断言是手写 if，一个函数测三种情况要写三遍 if got != want。扩展包 testify 的 require 和 assert 能一行断言，还附带错误信息：

```go
package calc

import (
	"testing"

	"github.com/stretchr/testify/assert"
	"github.com/stretchr/testify/require"
)

func TestAddAssert(t *testing.T) {
	assert.Equal(t, 3, Add(1, 2))
	assert.NotEqual(t, 4, Add(1, 2))
	assert.NoError(t, nil)
	assert.Empty(t, "")
}
```

assert 和 require 的区别是对失败的处置：

| 断言风格 | 失败后行为 |
|---|---|
| assert.Equal | 记录失败，继续跑当前测试 |
| require.Equal | 立即终止当前测试 |

和标准库的 Error/Fatal 一一对应。如果断言失败后续无法执行（比如铁定要用的变量没拿到），用 require；只是想列出所有问题，用 assert。断言库只是语法糖，不改变测试逻辑，选一个用。

## 接口隔离：先抽象再 mock

真实代码几乎都要碰外部依赖：数据库、HTTP 服务、文件、第三方 SDK。单元测试的原则是测自己的逻辑，不测别人的服务。做法是把依赖抽象成接口，测试里用假实现替换。用一个例子说明抽象带来的好处。

假想一个用户服务需要一个仓库保存用户：

```go
// repository.go 定义最小接口，短小、贴近使用方
type UserRepo interface {
	Get(id int) (User, error)
	Save(u User) error
}

type UserService struct {
	repo UserRepo
}

func (s *UserService) GetName(id int) (string, error) {
	u, err := s.repo.Get(id)
	if err != nil {
		return "", err
	}
	return u.Name, nil
}
```

生产代码里放一个真实实现连数据库，测试里放一个假实现，不碰数据库：

```go
// repository_test.go
type fakeRepo struct {
	users map[int]User
}

func (f *fakeRepo) Get(id int) (User, error) {
	if u, ok := f.users[id]; ok {
		return u, nil
	}
	return User{}, errors.New("not found")
}
func (f *fakeRepo) Save(u User) error { return nil }

func TestGetName(t *testing.T) {
	svc := &UserService{repo: &fakeRepo{users: map[int]User{1: {Name: "tom"}}}}

	name, err := svc.GetName(1)
	require.NoError(t, err)
	assert.Equal(t, "tom", name)

	_, err = svc.GetName(99)
	assert.Error(t, err) // 不存在也要覆盖
}
```

关键点：接口本来就该为调用方而生，抽象不是为了测试硬加的，而是把真正的边界画清楚。测试用假实现验证服务逻辑，速度快、可重复、不花数据库连接。

## mock 库生成桩实现

依赖多、方法多时手写假实现很累。可以用 mock 库自动生成桩，比如 testify 组件里的 mock，配合 mockery 工具从接口生成。mock 的好处是能预设方法返回、统计调用次数。

```go
package calc

import (
	"testing"

	"github.com/stretchr/testify/assert"
	"github.com/stretchr/testify/mock"
)

type MockUserRepo struct {
	mock.Mock
}

func (m *MockUserRepo) Get(id int) (User, error) {
	args := m.Called(id)
	return args.Get(0).(User), args.Error(1)
}

func TestGetNameWithMock(t *testing.T) {
	repo := new(MockUserRepo)
	repo.On("Get", 1).Return(User{Name: "tom"}, nil)

	svc := &UserService{repo: repo}
	name, err := svc.GetName(1)
	assert.NoError(t, err)
	assert.Equal(t, "tom", name)

	repo.AssertCalled(t, "Get", 1) // 确认确实调用了
}
```

mock 比手写假实现多了行为断言，能检查被测代码是否真的调用了依赖、以什么参数调用。但样板上限也在此：mock 和真实实现之间可能发生漂移，接口改了 mock 忘了更新就会误报绿。权衡是：很少的依赖用手写假实现，依赖复杂且稳定再用 mock 工具。

## 临时文件与临时目录

要测文件读写又不污染仓库，用 t.TempDir() 建临时目录，测试结束自动清理：

```go
func TestWriteFile(t *testing.T) {
	dir := t.TempDir()
	path := filepath.Join(dir, "a.txt")
	if err := os.WriteFile(path, []byte("hi"), 0644); err != nil {
		t.Fatal(err)
	}
	data, _ := os.ReadFile(path)
	assert.Equal(t, "hi", string(data))
}
```

掉在磁盘上的临时文件由框架负责清除，不用自己记着删。要测 HTTP 接口，用 httptest.NewServer 起本地服务，同样不依赖外网。

## 测试策略：优先级与边界

有了工具，最重要的还是知道测什么。给测试排优先级，收益集中在少数几类：

优先级最高，几乎必须写：
- 核心算法与业务规则：所有分支（if/switch 的每个出口）
- 错误路径：输入非法、资源不存在、返回 err 时怎么收尾
- 公共 API：别人调你的函数，契约不能悄悄变

值得写但不必面面俱到：
- 边界值：空、零、超长、最大值、极小的负值
- 并发正确性：用 -race 并发跑，见并发篇
- 序列化：JSON 字段、时区、编码

投入产出比较低：
- 纯 getter/setter 和脚手架
- 拷贝粘贴的 UI 模板

边界测试是发现漏洞的高产矿。回看上一张表的例子：正数、负数、零、大数都测，恰恰因为整数运算在正负零和溢出处最容易出昏招。

## 向测试里注入超时

被测函数可能空转或卡死，测试里用 context 超时兜底，让挂掉的测试尽快失败而不是干等：

```go
func TestSlowOp(t *testing.T) {
	ctx, cancel := context.WithTimeout(context.Background(), time.Second)
	defer cancel()
	err := someOp(ctx)
	require.NoError(t, err)
}
```

## 小结

工程化测试的支柱是三条：用 testify 这类断言库少写样板、把外部依赖抽象成接口并用假实现或 mock 隔离、按核心算法到边界值的优先级分配测试精力。策略上记住测试价值集中在分支、错误路径和公共契约，别在脚手架和复制粘贴的代码上消耗太多。测试不是数量游戏，是风险对冲。
