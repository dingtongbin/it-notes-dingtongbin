# 依赖治理与版本

Go 的依赖管理围绕 go.mod 展开，版本选择规则、工作区、发布与治理清单。这一篇补齐工程化的另一半。

## 版本选择：最小版本选择（MVS）

```bash
go get github.com/x/y@v1.5.0     # 精确升级
go get -u ./...                  # 升级所有直接依赖到最新次要版本
go get -u=patch ./...            # 只升补丁版本
go list -m -versions github.com/x/y    # 查所有可用版本
```

MVS 语义是"选满足所有依赖要求的最小版本"，不是最新。A 要 x 的 1.2、B 要 x 的 1.4，最终选 1.4；C 要 x 的 1.3 不会把整体拉到 2.0。结果是可复现且保守的。与 npm 的"各自嵌套多版本"不同，Go 依赖树里每个模块只有一个版本。

## replace 与工作区

调试 fork、本地联调时用 replace 临时替换：

```go
// go.mod
replace github.com/you/lib => ../lib
replace github.com/upstream/patched => github.com/you/patched v1.0.1-fix
```

多模块同仓开发用 workspace，比一排 replace 干净：

```bash
go work init ./cli ./lib         # go.work 把本地模块联起来（go.work 不进 git）
```

## 依赖治理清单

```bash
gofmt -s ./...                   # 格式化
go vet ./...                     # 内置静态检查
golangci-lint run                # 聚合 linter（生产标配）
go test ./... -race              # 竞态检测（并发代码必跑）
govulncheck ./...                # 官方漏洞扫描
go mod verify                    # 校验 go.sum 完整性
go mod tidy                      # 校准 go.mod/go.sum（保存代码后必跑）
```

go.mod 的治理信号：依赖数异常多要审计引入必要性，Go 生态崇尚标准库优先；带 // indirect 注释的是间接依赖，是 tidy 的产物，正常。

## 版本与发布

```bash
git tag v1.2.0 && git push origin v1.2.0    # Go 模块版本 = git tag（semver）
```

版本号遵循 semver。v2 及以上的大版本有个特殊规则：模块路径要带版本后缀，import 路径跟着变：

```go
// go.mod
module github.com/you/lib/v2
// 使用方
import "github.com/you/lib/v2/pkg"
```

主版本升级等于换 import 路径，新旧版本可以共存，彻底避免破坏性升级的连锁爆炸。

## 常见坑

第一个坑：忘了 go mod tidy，IDE 能补齐 import 但 go.mod 没记录，CI 构建失败。

第二个坑：调试用的本地 replace 忘了删，带上生产环境，别人构建报路径不存在。

第三个坑：tag 了 v2 但 module 路径没加 /v2 后缀，使用者拉不到。
