# 切片原理与内存

切片不是"动态数组"的黑盒，理解它的底层结构（指针 + 长度 + 容量）才能解释 append 的行为和传参语义。这一篇讲透切片头和共享底层数组的陷阱。

## 切片的底层结构

```go
s := []int{1, 2, 3, 4, 5}    // []int：不定长
fmt.Println(s, len(s), cap(s))   // [1 2 3 4 5] 5 5
```

切片头是三个字段的小结构体：

```go
// 切片头（slice header）
// array 指针：指向底层数组
// len   长度：元素个数
// cap   容量：底层数组大小
```

切片本身只有约 24 字节，真正的数据在底层数组里。赋值或传参拷贝的是这个"头"，但指针共享同一块底层数组：

```go
a := []int{1, 2, 3}
b := a                  // 共享底层数组
b[0] = 99
fmt.Println(a)          // [99 2 3]！和 Python 可变列表的赋值行为一致

func modify(s []int) { s[0] = 88 }
modify(a)
fmt.Println(a)          // [88 2 3]：函数能改到原数据
```

## 切片表达式：共享底层数组的陷阱

切出子切片后，子切片和原切片共享同一块底层数组。这带来一个高发 bug：

```go
s := []int{1, 2, 3, 4, 5}
sub := s[1:4]              // [2 3 4]，len=3
fmt.Println(sub, len(sub), cap(sub))   // [2 3 4] 3 4

// 陷阱：sub 与 s 共享底层数组！
sub[0] = 999
fmt.Println(s)             // [1 999 3 4 5]
```

更危险的是 append：容量够时直接写进共享的底层数组，会改坏原切片：

```go
sub = append(sub, 6)       // cap(4) 够，写进 s[4] 的位置
fmt.Println(s)             // [1 999 3 4 6]！！s 被改了

sub = append(sub, 7)       // cap 不够，分配新底层数组，sub 搬家
sub[0] = -1
fmt.Println(s)             // 不再受影响（已经不共享了）
```

隔离手段有两个：

```go
// 完整拷贝（三参数切片表达式：限制容量，append 必然搬家）
safe := s[1:4:4]           // len=3, cap=3
// 或显式 copy
copy1 := make([]int, len(s))
n := copy(copy1, s)        // copy 返回拷贝的元素数
```

## 常见坑

第一个坑：截取后 append 污染原切片，是面试和线上 bug 的双重高发区，用三参数切片或 copy 隔离。

第二个坑：以为传切片进函数是拷贝数据，实际拷贝的只是头，底层数组共享，函数内能改到原数据。
