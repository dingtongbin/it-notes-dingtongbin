# 包管理与项目结构

环境篇讲了 go mod 基础，这一篇补齐工程化：标准项目布局、internal 封装、包设计纪律。

## 标准项目布局

一个标准 Go 工程长这样：

```
myapp/                          # GitHub 仓库根 = 模块根
├── go.mod                       # module github.com/you/myapp
├── main.go                      # package main（简单项目入口就在根）
├── internal/                    # 编译器强制私有：只有本模块可导入
│   ├── terminal/
│   │   └── session.go
│   ├── ssh/
│   │   └── client.go
│   └── config/
│       └── config.go
├── pkg/                         # 可选：明确对外公共的库代码
│   └── credentials/
├── cmd/                         # 多可执行入口才需要
│   ├── server/main.go
│   └── cli/main.go
└── docs/
```

三条结构纪律：

第一，internal 是 Go 的杀手锏，编译器保证外部项目 import 不了你的内部包，这是 Python、JS 做不到的强制封装。

第二，包按领域命名（terminal、ssh、config），不按类型（models、helpers、utils 是反模式）。

第三，main 薄：main.go 只做装配（读配置、连依赖、启动），业务全在 internal 包里，可测试性来自这里。

## 可见性与 Package 申明细节

目录名等于包名，全小写无下划线。包内大写开头导出，小写私有。除了入口 main 包，其他包不要用 package main。

## 包的设计纪律

```go
// 好的包：单一领域、明确导出面
package ssh

var ErrAuthFailed = errors.New("auth failed")   // 哨兵错误导出

type Client struct { ... }                       // 主类型
func NewClient(cfg Config) (*Client, error)      // 构造
func (c *Client) Run(cmd string) (string, error) // 操作
func Dial(addr string) (*Client, error)          // 便捷入口
```

导出最小面：能私有就私有，导出的每个名字都是升级包袱。

包级状态最小化：全局可变状态是测试和并发的敌人，用结构体持有状态。

## 常见坑

第一个坑：main.go 巨型化，逻辑全塞入口，无法单测。装配薄、领域包厚。

第二个坑：utils、helpers 泛滥，说明没有领域划分，按功能域拆包。

第三个坑：循环依赖即设计问题，编译器第一时间报错，抽接口或往下沉公共包。
