# 版本策略与应用内更新

程序不会永远停在发布那天。版本号怎么定、用户手里的旧版本怎么更新到新版，是一个桌面应用发布闭环的重要一环。这一篇讲语义化版本和最简单实用的应用内更新做法。

## 语义化版本

版本号统一用主.次.补丁三段式：

```
v1.2.3
│ │ └─ 补丁：bug 修复（1.0.0 → 1.0.1）
│ └─── 次版本：新功能，向后兼容（1.0 → 1.1）
└───── 主版本：破坏性变更（1.x → 2.0）
```

约定清楚，用户和代码都能从版本号推断这次改动的影响范围。主版本升级因为可能有破坏性变更，一般要更谨慎。

## 应用内检查更新

最简单的刷新逻辑是：启动时请求仓库最新的 Release 版本号，和自己比，不一样就提示。

```go
type UpdateInfo struct {
	Latest string
	URL    string
}

func (s *AppService) CheckUpdate() (*UpdateInfo, error) {
	resp, err := http.Get("https://api.github.com/repos/you/aceshell/releases/latest")
	if err != nil {
		return nil, fmt.Errorf("check update: %w", err)
	}
	defer resp.Body.Close()

	var rel struct {
		TagName string `json:"tag_name"`
		URL     string `json:"html_url"`
	}
	if err := json.NewDecoder(resp.Body).Decode(&rel); err != nil {
		return nil, fmt.Errorf("decode release: %w", err)
	}
	if rel.TagName != "v"+version {
		return &UpdateInfo{Latest: rel.TagName, URL: rel.URL}, nil
	}
	return nil, nil    // 已是最新
}
```

前端在启动时调用，如果有新版就弹提示，用户点开跳转到发布页下载。这个方案的优点是零额外依赖，只要一个能查最新版本的接口。

## 版本比较的注意

字符串直接比较 rel.TagName != version 在版本号长度不一致时可能出错，比如 v10 和 v9。严格做法是把版本号按主.次.补丁拆开逐段比较。小项目先做雏形可以灵活，但要知道这个坑存在。

## 进阶：自动下载更新

要更进一步做到自动下载、签名校验、静默重启，思路和 electron-updater 类似：查版本、下载增量或全量包、校验签名、替换二进制、重启。变化是无感的，比让用户手动跳下载页体验好，但要多做下载、签名校验、回滚这些工作。

## 常见坑

1. 版本号漂移：tag 打了 v1.2.0，二进制里还是 dev，版本必须由 CI 注入。
2. 版本比较用错：直接字符串比在位数不同时出错，要分段比较。
3. 大升级丢数据：版本升级时配置/数据格式变化，要有迁移逻辑，否则旧数据读不出来。
