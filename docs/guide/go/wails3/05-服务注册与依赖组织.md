# 服务注册与依赖组织

一个桌面应用不会只有一个服务。随着功能变多，需要把能力按领域拆成多个服务，再统一注册给框架。这一篇讲怎么组织多个服务、怎么用目录结构把代码分境。

## 注册多个领域服务

RegisterService 可以调用多次，每个领域一个服务：

```go
app.RegisterService(terminal.NewService())   // 终端/PTY 管理
app.RegisterService(ssh.NewService())        // SSH 会话
app.RegisterService(sftp.NewService())       // 文件传输
app.RegisterService(NewAppService())         // 系统信息
```

前端按服务拿绑定：terminal 服务的方法从前端一个命名空间导入，ssh 服务是另一个。服务之间按域名隔离，互不干扰，这是把大型功能拆开的基础。

## 后端目录结构

服务多了以后，源码按领域放：

```
internal/
├── terminal/     # PTY 会话
├── ssh/          # ssh 客户端封装
├── sftp/         # 文件传输
├── crypto/       # 凭据加密
└── config/       # 会话存储（TOML）
```

每个目录是一个包，各自封装自己的职责，对外只暴露 NewService 之类的方法，由 main 统一装配。

## 装配与分层原则

后端结构的组织原则和 web开发章节的分层架构一致：

- main 只做装配：创建应用、注册服务、跑起来，不写业务逻辑。
- internal 按领域分包，各自管好自己的依赖。
- 服务是 Go 世界对前端暴露的 API 层，方法就是前端的接口。

这样前端面对的是一个清晰的领域模型，而不是一堆散落的方法。新增一个功能 = 加一个领域目录 + 写一个服务 + 在 main 里注册一行。

## 绑定约束带来的习惯

因为能被绑定的方法要求导出类型、导出字段，写服务时自然会被迫做干净：返回给前端的结构体字段全部导出且有 JSON 标签。这其实是好事，等于强制明确了前后端的数据契约。

## 常见坑

1. 字段没导出：返回类型里混进了小写字段，绑定失败或字段缺失。
2. 服务没注册：前端 import 到了但调用报错，回到 main 检查注册。
3. 目录职责不清：什么都放一个包里，难维护，坚持一个领域一个包。
