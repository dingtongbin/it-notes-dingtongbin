# 上架商店与发布清单

除了官网和 Release 页，很多桌面应用会走应用商店这条分发渠道。Windows 有微软商店（MSIX），这条链路对独立开发者尤其友好，因为签名由商店处理、自带自动更新。这一篇讲上架流程，最后给一份可照着执行的发布清单。

## 上架微软商店的流程

商店分发的主打卖点：签名由商店处理（省掉自购代码签名证书的成本），自带 Windows 自动更新，用户从商店安装更放心。

```
1. 打包 MSIX：用 Windows SDK 的 MakeAppx 或框架的商店打包任务
2. 注册开发者账号：微软合作伙伴中心，个人账号一次性费用
3. 填写商品信息：描述、截图（多分辨率）、分级问卷、隐私声明 URL
4. 上传 MSIX 并提交 → 认证（安全扫描 / 合规 / 内容审查）
5. 上架后可配置：分阶段发布（按百分比放量）、自动更新走商店
```

从打包到过审有一套固定动作，能不能上架取决于材料是否齐、是否有崩溃。

## 审核常见被拒原因

- 崩溃：真实机器上全功能测过再提交，启动即崩是最常见的坑。
- 隐私声明缺失：有隐私行为的应用必须提供可访问的隐私声明 URL。
- 与描述不符：截图和实际功能出入太大，功能描述夸大。

对策就是提交前把这三件事逐个确认，把验收动作列进清单。

## 发布清单

发布前逐条自查，任何一条不满足都不该发布：

```
[ ] 版本号三处一致：git tag / build/config.yml / 关于页
[ ] 前端 npm run build 通过（包含类型检查）
[ ] go vet + golangci-lint + go test -race 全绿
[ ] 三平台真机冒烟：启动 / 核心功能 / 崩溃率
[ ] Windows：无签名时提交杀软误报申诉（提前 1~2 周）
[ ] macOS：签名 + 公证 + Gatekeeper 实测
[ ] Linux：三个发行版（Ubuntu / Arch / Debian）抽测依赖
[ ] 旧配置兼容：升级安装后旧会话、凭据文件可读（版本迁移逻辑）
[ ] 卸载干净：安装目录、配置目录的清理与保留策略明确
[ ] Release Notes 写清楚：新功能 / 修复 / 已知问题
```

## 几个容易忽略的点

杀软误报要提前处理：未签名的 Windows 程序被误报是常态，申诉周期一周到两周，别等发布前才想起。升级不丢数据：配置文件或数据格式变了却没迁移逻辑，用户一升级旧数据就没了，这是大版本升级最痛的地方。

## 总结

到这一篇，桌面应用从建工程、前后端绑定、窗口托盘、打包发布到商店上架全链路闭环了。剩下的工作就是把清单执行到位：版本、质量、平台、数据兼容每一项到位，发布就只是例行公事。
