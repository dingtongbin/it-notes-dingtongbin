# 构建与版本注入

开发调试好了，接下来要产出可发布的程序。这一篇讲构建命令、跨平台编译、以及版本信息怎么在编译时注入二进制。它会接到下一篇讲具体的安装包打包。

## 构建当前平台

标准流程是先构建前端，再编 Go：

```bash
cd frontend && npm ci && npm run build && cd ..

wails3 task build
# 产物：build/bin/aceshell.exe（Windows 上）
```

任务流水线通常会帮你把前端也构建好，顺序固定为先前端后 Go，因为 Go 需要 embed 已经构建好的 frontend/dist。

## 跨平台编译

同一份代码可以交叉编译到不同平台：

```bash
wails3 task build -platform windows/amd64
wails3 task build -platform linux/amd64
wails3 task build -platform darwin/universal   # macOS 通用二进制（x86 + ARM）
```

darwin/universal 指同时包含 Intel 和 Apple Silicon 架构的通用二进制。注意交叉编译通常需要目标平台对应的构建工具链，macOS 的产物一般还是要在一台 Mac 上编。

## 版本信息注入

给二进制注入版本号、git 提交、构建时间，是发布专业化的基础。标准做法是 ldflags：

```bash
go build -ldflags "-X main.version=1.0.0 -X main.commit=$(git rev-parse --short HEAD)"
```

Go 侧用包级变量接住：

```go
package main

var version = "dev"    // 由 -ldflags 注入
var commit = "unknown"
```

这样关于对话框、更新检查里读到的版本号，都来自编译时注入，而不是手写死，避免版本漂移。

## 产物自包含

关键认知：前端资源已经被 embed 进二进制，所以产物是自包含单文件。用户拿到这一个文件就能跑，不需要装 Node、不需要凑 Chromium——这正是相比 Electron 包体小一个量级的原因。

## 常见坑

1. 前端没构建就编 Go：embed 目录缺失直接编译失败，流水线必须先前端后 Go。
2. 版本号手写不统一：版本信息要走 ldflags 注入，别在代码里写死。
3. CI 和本地不一致：本地能编 CI 不行，多半是系统依赖，用固定环境构建。
