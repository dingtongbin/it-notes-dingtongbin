# 事件架构设计规则

前面几篇把绑定、事件、多窗口、托盘、菜单逐个讲了。设计一个真正可维护的桌面应用，需要把这些串成一套统一的架构规则。这一篇用一个完整的架构图收口，并给出几条硬性的设计纪律。

## 架构总览

一个运维终端类应用，前后端协作大概长这样：

```
┌────────── 渲染进程（Vue）──────────┐
│  会话树 / 终端 UI / 进度条 / 设置    │
└──────┬──────────────┬──────────────┘
   绑定方法(请求)      Events.On(推送)
       │                  ↑
┌──────┴──────────────────┴──── Go 主进程 ────┐
│  Service 层：terminal / ssh / sftp / vault  │
│  后台 goroutine：PTY 读写 / 传输 / 心跳      │
│  事件源：状态变化 → EmitEvent               │
└─────────────────────────────────────────────┘
```

前端负责界面和轻量的展示状态，Go 侧承担所有真实逻辑，靠绑定和事件两条通道连接。

## 三条硬规则

### 1. 长任务全部异步

所有有耗时的操作，比如连接、传输、录制，都必须起后台 goroutine，不能堵在绑定方法里等完成。绑定方法快速返回，真正的工作在后台跑，进度靠事件汇报。

### 2. 事件名带领域前缀，payload 用结构体

事件名用 sftp:、terminal:、app: 这种前缀命名，payload 尽量用带齐 JSON 标签的结构体而不是裸的零散字段。这样前端订阅时能拿到稳定的字段集合，而不是猜。

### 3. 前端退订与组件生命周期对齐

订阅事件返回的取消函数必须在组件卸载时调用（onUnmounted）。否则组件销毁了监听还在，重复触发、内存泄漏一起找上门。

## 事件类型化封装

前端可以把订阅封装成带泛型的组合式函数，自动退订加类型收窄：

```typescript
function useWailsEvent<T>(name: string, handler: (data: T) => void) {
  const off = Events.On(name, handler);
  onUnmounted(off);
}
```

所有业务事件统一走它，就避免了裸用任何卸载时忘记退订的问题。事件 payload 在职责层面是 any，前端在封装层收窄成明确类型。

## 常见坑

1. 监听泄漏：组件卸载不退订，事件重复触发。退订必须和生命周期对齐。
2. payload 类型丢失：事件数据是 any，要有 interface 收窄或统一的事件名到类型的映射表。
3. 高频事件刷屏：每字节都发事件会卡 UI，节流或用偏移量让前端自己算进度。
4. 多窗口广播误伤：EmitEvent 全窗口都收，定向场景用窗口级 Emit。
