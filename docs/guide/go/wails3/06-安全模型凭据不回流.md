# 安全模型：凭据不回流前端

桌面应用经常处理敏感数据，比如运维终端的服务器密码、SSH 会话的凭据。一个重要的设计原则是：敏感材料永远留在 Go 进程内，不回传前端。这一篇讲这样的架构怎么落地。

## 为什么敏感数据不能进前端

前端跑在 WebView 里，本质上是一段可被脚本执行的代码。一旦密码、密钥被送到前端：

- 任何注入的前端代码都能读走
- DevTools 里就能看到明文
- 智能体、自动化脚本可能基于它做不该做的事

结论是：前端（以及经由前端的任何层）只能触发动作和拿状态，真正的敏感材料只能待在 Go 进程里。

## Go 侧持有凭据，前端只拿状态

典型做法是凭据由 Go 加密存储，连前端都不要传：

```go
// 凭据不回传前端，只在 Go 侧解开用
func (s *AppService) Connect(sessionID string) error {
	cred, err := vault.Get(sessionID)      // 从加密存储解出，不发给 JS
	if err != nil {
		return err
	}
	return terminal.Connect(sessionID, cred)
}
```

前端能拿到的只是一份状态描述，里面没有密码：

```go
type SessionStatus struct {
	ID     string `json:"id"`
	State  string `json:"state"`    // connecting/connected/closed
	Uptime int    `json:"uptime"`
}
```

前端发起 Connect，返回的是连接状态；真正用到的凭据全程在 Go 侧。这样即使前端被攻破，也摸不到密码。

## 加密存储的思路

凭据在磁盘上也不能是明文，通常用系统相关的方式加密：

- Windows 上类似 DPAPI 的思路，用当前用户/机器绑定一个密钥。
- 加密算法用 AES-GCM，密钥从机器绑定密钥派生。
- 存成 TOML 或独立文件，读取时校验篡改。

具体实现里 crypto 包只负责加解密的机械操作，vault 负责密钥管理和读写文件，都在 Go 侧，前端完全接触不到。

## 对比：什么数据可以放心给前端

| 数据 | 是否适合进前端 |
|---|---|
| 连接状态、会话列表、传输进度 | 可以，属于展示状态 |
| 服务器地址、端口、用户名（非敏感） | 可以 |
| 密码、私钥、token | 不可以，只留在 Go 侧 |

判断标准很简单：偷走会不会造成损失。会，就留在 Go 里。

## 设计上的收益

这个约束其实让接口更干净：前端只需要动作和状态两种东西，Go 侧承担真正的敏感逻辑。安全和边界一起被理清了。

验证方法：跑起来之后在 DevTools 里搜密码关键字，应该任何地方都找不到明文；发起的连接流程前端只能看到状态枚举变化。
