# 参数绑定与校验

上一章读了 query、路径参数、表单，但请求体里的 JSON 还停留在手动读取。这一篇讲 Gin 最舒服的输入处理方式：把请求体一键绑到结构体，再通过 tag 做校验。绑定加校验是 Gin 相比裸编写标准库的巨大优势，也是平时写接口最常用的一步。

## 为什么用绑定

手写 json.Unmarshal 加上手动判断每个字段，接口一多就到处是重复代码，而且容易漏校验。Gin 的绑定把两件事一起做了：

- 反序列化：把 JSON 或表单自动填进结构体
- 校验：根据 tag 里的规则检查合法性

```go
type CreateUserReq struct {
	Name  string `json:"name"  binding:"required"`
	Email string `json:"email" binding:"required,email"`
	Age   int    `json:"age"   binding:"gte=0,lte=150"`
}
```

## 基本绑定：ShouldBindJSON

ShouldBindJSON 从 JSON body 反序列化并执行校验，失败会返回错误：

```go
r.POST("/users", func(c *gin.Context) {
	var req CreateUserReq
	if err := c.ShouldBindJSON(&req); err != nil {
		c.JSON(400, gin.H{"error": err.Error()})
		return
	}
	// req 字段已填好且通过校验
	c.JSON(201, gin.H{"name": req.Name, "email": req.Email})
})
```

校验失败时，err 里带的是英文的底层描述，直接返回给前端不够友好。工程里通常再包一层，把具体的失败点翻译成可读信息，后面统一错误章节处理。

## 绑定来源：ShouldBind 自动判断

如果只写 ShouldBind，Gin 会按照 Content-Type 自动选择绑定器：JSON body 走 ShouldBindJSON，表单走 form，query 参数也可以绑。这样同一个结构体既能接 body 又能接参数：

```go
type ListReq struct {
	Page int    `form:"page"`
	Size int    `form:"size"`
	Name string `form:"name"`
}

r.GET("/hosts", func(c *gin.Context) {
	var req ListReq
	if err := c.ShouldBind(&req); err != nil {
		c.JSON(400, gin.H{"error": err.Error()})
		return
	}
	c.JSON(200, req)
})
```

这里 GET 请求用 form tag 绑 query。ShouldBind 的结语是"让你少想来源"：约定好内容类型后一个调用搞定，省得每个接口都判断来源再挑绑定器。

## 常用的校验 tag

校验规则来自 validator 库，binding 标签里的逗号分隔多条规则。日常最常用的一批：

```go
type Req struct {
	Name    string `binding:"required"`                 // 非空
	Email   string `binding:"email"`                    // 合法邮箱
	Age     int    `binding:"gte=0,lte=120"`            // 范围
	URL     string `binding:"url"`                      // 合法 URL
	Phone   string `binding:"len=11,numeric"`           // 长度加全是数字
	Service string `binding:"required,oneof=web api"`   // 枚举白名单
	DevIP   string `binding:"ip"`                       // 合法 IP 地址
}
```

需要总结规律先把一把规则记住：required 非空、email 邮箱、url 链接、ip 地址、numeric 纯数字、len 精确长度、min 与 max 范围、gte 与 lte 数值上下限、oneof 枚举、alphanum 字母数字。这些覆盖了绝大多数接口的录入校验。

数组成员规则用字符串下标或整体校验，例如数组里的每个元素都非空：

```go
type Req struct {
	Tags []string `binding:"required,dive,required"`
}
```

dive 表示进入结构体或切片的成员再套用后面的规则。这是复杂嵌套校验和必会，但别贪，超过两层深度的校验建议移到业务层。

## 自定义校验

内置规则不够时注册你自己的校验函数。比如校验一个字段必须符合某种自定义格式：

```go
import "github.com/gin-gonic/gin/binding"

// 自定义校验器
func isExact5Digits(fl validator.FieldLevel) bool {
	s := fl.Field().String()
	return len(s) == 5 && isAllDigit(s)
}

func setupValidator() {
	if v, ok := binding.Validator.Engine().(*validator.Validate); ok {
		_ = v.RegisterValidation("five_digits", isExact5Digits)
	}
}
```

注册后就能在 tag 里用自定义名字：

```go
type Req struct {
	Code string `binding:"five_digits"`
}
```

自定义校验函数里的 fl.Field() 拿到结构体字段的反射值，用它判断合法性。注意 RegisterValidation 需要在创建引擎之前调用一次，比如放 init 或 main 的开头。

## 用 time 解析与忽略字段

处理时间字段或只想接收部分字段时：

```go
type Req struct {
	CreatedAt time.Time   `json:"created_at" binding:"required,datetime=2006-01-02 15:04:05"`
	Internal  string      `json:"-"`          // 不暴露给 JSON，也不参与绑定
}
```

datetime 校验规则把字符串严格按给定布局解析，几遍手写 time.Parse 的方便。字段置成 json:"-" 表示完全忽略，既不出现在 JSON 输出，也不接收输入。

## 常见坑

第一个坑是 binding 校验失败返回的错误太底层。别直接把 err.Error() 丢给前端，通常要解析成字段和原因，这个见统一错误章节。

第二个坑是 GET 传参走了 ShouldBindJSON 或用 JSON body 走了 ShouldBind，结果绑定器不对拿不到值。GET 传参用 form tag，POST 请求体用 json tag，保持 Content-Type 与绑定器一致。

第三个坑是忘记处理必填字段的零值。required 检查的是字段非零值，int 类型的 0、string 的空串都会被判为不通过，想允许 0 又有范围就用 gte=0 而不是 required。

第四个坑是自定义校验器重复注册导致 panic。RegisterValidation 不能对同一个名字注册两次，改规则前先注销，或保证只在启动时注册一次。

第五个坑是嵌套结构体的校验规则写在父字段上而非子结构体上。子结构体类型字段直接写 binding 不生效，要在子结构体的字段上写，父字段只需标记 dive 或 required。
