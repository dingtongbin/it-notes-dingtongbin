# 项目分层架构

业务逻辑全写在 handler 里，前 10 分钟能跑，第 10 天开始要命：换协议就重写、想单测必须起真库、展示层和存储层搅成一团。这一篇定下三层规则、目录布局、依赖注入与错误流动，落成一个可维护的后端项目骨架。

## 业务逻辑写在 handler 里的三大死法

```go
// 反例：一个 handler 干完解析、业务、SQL、响应
func createHost(c *gin.Context) {
	var req CreateHostReq
	c.ShouldBindJSON(&req)             // 传输：解码
	if len(req.Name) < 2 { /* 校验 */ } // 业务：校验规则
	db.Where("name = ?", req.Name).First(&exist) // 数据：查重
	db.Create(&Host{...})              // 数据：写入
	Success(c, host)                   // 传输：编码
}
```

三个死法：无法复用（换协议就抄一遍）、无法单测（测业务要先起真库）、无法演进（换 ORM、加事务全是侵入式手术）。

## 分层规则：handler 到 service 到 repository

| 层 | 职责 | 禁止 |
|---|---|---|
| handler（传输层） | 解码请求、调 service、编码响应、错误转状态码 | 业务规则、SQL |
| service（业务层） | 业务规则、编排、事务边界 | 出现 *gin.Context、gorm.DB |
| repository（数据层） | 存取：SQL、缓存、内存 | 业务规则 |

依赖只能向内：service 不知道 HTTP 也不知道 GORM，它只认识自己定义的接口。

## 目录布局

```
myapi/
├── cmd/
│   └── server/main.go     # 一个二进制一个 main，只做组装
├── internal/
│   ├── config/            # viper 配置
│   ├── log/               # slog 日志
│   ├── service/           # 业务层 + 接口定义
│   ├── repository/        # 数据层实现（GORM）
│   └── transport/http/    # handler、中间件、DTO
├── configs/config.yaml
└── go.mod
```

cmd 只放组装不放业务；internal 是编译期私有，里面的包只有父目录树内的代码能 import，外部模块直接编译报错；禁止 utils 垃圾桶包，函数按领域归位。

## 手工依赖注入

不引 di 框架，构造函数加 main 组装，编译期就能查出缺了哪个依赖：

```go
// cmd/server/main.go：唯一的组装点
func main() {
	cfg, err := config.Load("configs/config.yaml")
	if err != nil {
		log.Fatal(err)
	}
	db, err := gorm.Open(mysql.Open(cfg.MySQL.DSN), &gorm.Config{})
	if err != nil {
		log.Fatalf("open db: %v", err)
	}

	// 组装链：repo 实现 service 定义的接口，换实现只改这一段
	svc := service.NewHostService(repository.NewHostRepo(db))
	h := httphandler.NewHostHandler(svc)
	// ... 注册路由、启动
	_ = h
}
```

换个内存实现做演示程序，只改 main 的组装链，service 与 repository 纹丝不动。这是依赖注入的核心价值。

## 依赖接口该定义在哪

重要的经验：接口跟使用方走。service 声明它需要什么行为，repository 去实现它，方向是单向的：

```go
// internal/service/host.go：接口长在使用方 service，不在 repository
type HostRepo interface {
	Create(ctx context.Context, h *Host) error
	GetByID(ctx context.Context, id int64) (*Host, error)
}
```

接口只放用得到的方法，按需最小化。这样 service 不 import repository，repository import service 实现其接口。循环依赖的破法就是靠这种依赖倒置：每一方定义自己需要的接口，由对方实现，main 负责接线。

## 错误的跨层流动

| 方式 | 写法 | 适用 |
|---|---|---|
| 哨兵错误 | var ErrHostNotFound = errors.New(...) | 可预期、调用方要判等的关键错误 |
| 自定义类型 | type ValidationError struct | 携带结构化信息 |
| %w 包装 | fmt.Errorf("create host: %w", err) | 层层加上下文，保留判断链 |

哨兵错误定义在 service，repository 把底层错误翻译成它。handler 是唯一的错误转状态码的地方：

```go
func statusFromErr(err error) int {
	var ve *service.ValidationError
	switch {
	case errors.Is(err, service.ErrHostNotFound):
		return http.StatusNotFound
	case errors.As(err, &ve):
		return http.StatusUnprocessableEntity
	case errors.Is(err, context.DeadlineExceeded):
		return 504
	default:
		return 500
	}
}
```

两条铁律：service 永远返回 error，打日志后 return nil 等于吞错误；翻译只发生在 handler，翻译一次。

## 一个完整示例：资产管理

领域模型住在 service，干干净净不带 json tag：

```go
// internal/service/host.go
package service

type Host struct {
	ID        int64
	Name      string
	IP        string
	CreatedAt time.Time
}

type HostService struct {
	repo HostRepo
}

func NewHostService(repo HostRepo) *HostService { return &HostService{repo: repo} }

func (s *HostService) Create(ctx context.Context, h *Host) error {
	if len(strings.TrimSpace(h.Name)) < 2 {
		return &ValidationError{Field: "name", Reason: "至少 2 个字符"}
	}
	if net.ParseIP(h.IP) == nil {
		return &ValidationError{Field: "ip", Reason: "不是合法 IP"}
	}
	h.CreatedAt = time.Now()
	if err := s.repo.Create(ctx, h); err != nil {
		return fmt.Errorf("create host: %w", err) // %w 保住判断链
	}
	return nil
}
```

repository 用 GORM，GORM 模型与领域模型分离，只在 repo 内转换：

```go
// internal/repository/host.go
type HostModel struct {
	ID        int64 `gorm:"primaryKey"`
	Name      string `gorm:"uniqueIndex;size:64"`
	IP        string `gorm:"size:45"`
	CreatedAt time.Time
}

func (HostModel) TableName() string { return "hosts" }

type hostRepo struct{ db *gorm.DB }

func NewHostRepo(db *gorm.DB) HostRepo { return &hostRepo{db: db} }

func (r *hostRepo) GetByID(ctx context.Context, id int64) (*service.Host, error) {
	var m HostModel
	if err := r.db.WithContext(ctx).First(&m, id).Error; err != nil {
		if errors.Is(err, gorm.ErrRecordNotFound) {
			return nil, service.ErrHostNotFound // 翻译，不暴露 gorm
		}
		return nil, fmt.Errorf("query host %d: %w", id, err)
	}
	return &service.Host{ID: m.ID, Name: m.Name, IP: m.IP, CreatedAt: m.CreatedAt}, nil
}
```

handler 定义 DTO，解码请求、调 service、编码响应：

```go
// internal/transport/http/host.go
type createHostReq struct { // 请求 DTO
	Name string `json:"name"`
	IP   string `json:"ip"`
}

func (h *HostHandler) create(c *gin.Context) {
	var req createHostReq
	if err := c.ShouldBindJSON(&req); err != nil {
		Fail(c, 400, 400, "参数错误")
		return
	}
	host := &service.Host{Name: req.Name, IP: req.IP}
	if err := h.svc.Create(c.Request.Context(), host); err != nil {
		Fail(c, statusFromErr(err), 1, err.Error())
		return
	}
	Success(c, host)
}
```

这个 pattern 就是 Go 版的依赖分层：handler 只做传输，service 只做业务，repository 只做存取。测试时替换 repository 为内存 fake，毫秒级跑完单测。

## 从单体到服务：拆分信号

先拆要付三张账单：网络延迟、分布式事务、运维复杂度。不是越早拆越好，看信号清单，满足三条以上再认真评估：

- 多个团队在同一代码库频繁 merge 冲突
- 模块资源画像差异巨大，必须独立伸缩
- 故障域需要隔离，模块崩溃不能带崩其他
- 各模块发布节奏差几个量级

决策原则：先单体，在进程内分层，等信号出现再沿 service 边界拆，接口已经在那里等着了。

## 常见坑

第一个坑是 service 直接依赖 *gorm.DB。这样 fake 无从做起，单测只能起真库。判断标准：删掉 repository 包，service 必须照样编译通过。

第二个坑是接口定义在实现方包造成循环 import。接口定义挪回使用方（service）方向立刻单向。

第三个坑是到处全局单例。db、logger 做成全局变量就测不了，依赖关系藏在代码里看不见。全走构造函数注入，main 是唯一组装点。

第四个坑是 DTO 与领域模型混用。service.Host 挂上 json tag，迟早被某个接口的特殊需求改坏。领域模型干干净净，传输形状放 handler 层转换。

第五个坑是错误在 service 被吞。打了日志就 return nil，handler 拿不到错误只能回 200。要么返回 error 让上层决策，要么注释写明这就是兜底终点。
