# 优雅退出与部署

服务写好之后，发布和关停是最后一步。这一篇解决两个问题：进程收到关闭信号时，如何优雅地停止接新请求、等存量请求处理完；以及 Go 服务常用的几种部署形态。优雅善后不是可选项，K8s、systemd 滚蛋时都要求这个能力。

## 为什么要优雅退出

直接 kill 进程，正在处理的请求会瞬间被掐断，用户端看到连接重置。优雅退出的目标是一个都不剩：不再接受新请求、给正在执行的请求留出时间、最后关资源。

## Gin 里用 http.Server 手动控制

gin.Default() 的 Run 是一行搞定，但优雅退出需要自己持有 http.Server，以便在收到信号后调用 Shutdown。需要的结构：

```go
func main() {
	r := gin.Default()
	r.GET("/ping", func(c *gin.Context) { c.JSON(200, gin.H{"ok": true}) })

	srv := &http.Server{
		Addr:    ":8080",
		Handler: r,
	}

	// 服务在 goroutine 里跑，不阻塞 main
	go func() {
		if err := srv.ListenAndServe(); err != nil &&
			err != http.ErrServerClosed {
			log.Fatalf("listen: %v", err)
		}
	}()

	// 监听关闭信号：Ctrl+C 或 kill
	quit := make(chan os.Signal, 1)
	signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
	<-quit // 阻塞在这里等信号

	// 收到信号：给存量请求 10 秒善后时间
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := srv.Shutdown(ctx); err != nil {
		log.Fatal("shutdown: ", err) // 超时后还有请求没处理完
	}
	log.Println("server exiting")
}
```

关键点：Shutdown 会停止接受新连接，并等待正在处理的请求完成；给它的 context 限定了最长等待时间，超过就强制结束。listener 关闭后 ErrServerClosed 是正常信号，不是错误，所以判断里要排除它。

signal.Notify 用带缓冲的 channel，防止信号来得太急把 main 卡住。收到 SIGTERM（K8s 滚动更新、systemd stop 都发这个）就会走完这条善后路径。

## 长时间的清理任务

Shutdown 只等 HTTP 请求完成，业务自己的后台任务（定时上报、后台 goroutine）要单独处理。常见的模式是和 context 联动：

```go
// 全局 context，业务后台任务都认它
ctx, cancel := context.WithCancel(context.Background())
go backgroundTask(ctx) // 后台任务监听 ctx.Done()

// 收到信号后先取消业务 context，再 Shutdown HTTP
<-quit
cancel() // 通知后台任务自己收尾退出
srv.Shutdown(shutdownCtx)
```

这样后台任务能在进程退出前优雅地释放资源，而不是被操作系统直接杀掉。对需要落盘的采集、上报类任务尤其重要。

## 部署形态一：直接跑二进制

Go 编译出单个可执行文件，拷贝到服务器直接跑。systemd 管理：

```ini
# /etc/systemd/system/api.service
[Unit]
Description=My Go API
After=network.target

[Service]
ExecStart=/opt/api/bin/myapi --config /etc/api/config.yaml
Restart=on-failure
User=www-data
Environment=GIN_MODE=release

[Install]
WantedBy=multi-user.target
```

systemd 停服务时发 SIGTERM，我们前面的优雅退出代码正好配合：systemd stop myapi 会触发信号处理的善后流程。

## 部署形态二：Docker 容器

多阶段构建把编译和运行分开，最终镜像里只有一个二进制，最干净：

```dockerfile
# 构建阶段
FROM golang:1.25 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o app ./cmd/server

# 运行阶段
FROM alpine:3.20
RUN adduser -D app
WORKDIR /app
COPY --from=build /src/app .
USER app
EXPOSE 8080
ENTRYPOINT ["./app"]
```

CGO_ENABLED=0 是纯 Go 的保证，编译出的二进制不依赖任何系统库，能在任何 Linux 基础镜像里跑。Gin 不涉及 cgo，可以放心开这个编译开关。

## 部署形态三：K8s 滚动更新

K8s 滚动更新时会给旧 Pod 发 SIGTERM，等待结束后才拉新业务。优雅退出的时长要和 K8s 的 terminationGracePeriodSeconds 匹配，Shutdown 的 context 超时不要长过 Pod 的宽限，否则请求还没处理完 Pod 就被强杀。

## 健康检查与就绪探针

部署后要有接口让负载均衡或 K8s 判定存活和就绪。写一个不依赖数据库的健康检查：

```go
r.GET("/healthz", func(c *gin.Context) {
	c.JSON(200, gin.H{"status": "ok"})
})
```

更完整的做法把依赖（DB、缓存）都检查一遍，返回 200 或 503。K8s 的 readinessProbe 会定期打这个接口，联机失败就暂时不把流量导向该实例。

## 常见坑

第一个坑是 ListenAndServe 错误没排除 ErrServerClosed。优雅退出时这个错误是正常现象，把它当错误打印 fatal 会让善后流程莫名其妙报错。

第二个坑是 Shutdown 的 context 超时设得太短。请求还没处理完就超时强制结束，和直接杀进程没区别。超时时间要大于最慢接口的预期耗时。

第三个坑是忘了处理后台任务。只 Shutdown 了 HTTP，后台 goroutine 还在跑，进程退出时它们被硬杀，数据可能丢。后台任务要和根 context 联动。

第四个坑是 CGO_ENABLED 忘了关。默认开启 cgo 编译出的二进制依赖 glibc，塞到 alpine 或 scratch 会跑不起来。纯 Go 项目编译时明确 CGO_ENABLED=0。

第五个坑是开发和生产模式不一致。Docker 里忘了设 GIN_MODE=release，以 debug 模式跑起来日志刷屏还变慢。发布脚本里显式设置环境变量。
