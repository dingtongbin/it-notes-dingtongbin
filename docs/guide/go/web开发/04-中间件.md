# 中间件

中间件是 Gin 最体现设计的一个概念：在请求进 handler 之前、或者在响应返回之后，插入一段共享的逻辑。日志、鉴权、panic 恢复、超时、CORS，这些横切关注点都能写成中间件，挂到需要的路由上。这一篇讲中间件的写法、挂载方式和几种典型实现。

## 中间件函数签名

中间件是一个接收 *gin.Context 的函数。它必须在最后调用 c.Next() 把控制权交给链路里的下一环；不调用 c.Next() 就表示拦截，直接终止请求：

```go
func myMiddleware() gin.HandlerFunc {
	return func(c *gin.Context) {
		// 进 handler 之前（前缀逻辑）
		start := time.Now()

		c.Next() // 放行，执行后面的 handler 和中间件

		// handler 返回后（后缀逻辑）
		elapsed := time.Since(start)
		log.Printf("took %v", elapsed)
	}
}
```

c.Next() 之前是请求前处理，之后是请求后处理，两个阶段夹着真正的业务 handler。这就是洋葱模型：请求从外层中间件一层层穿进去，响应再一层层穿出来。

## 挂载方式

中间件有三种挂法，作用范围不同：

```go
// 1. 全局：所有请求都经过
r.Use(Logger(), Recovery())

// 2. 分组：只对该分组下的路由生效
admin := r.Group("/admin")
admin.Use(AuthRequired())
admin.GET("/stats", statsHandler)

// 3. 单个路由：只对这一条生效
r.GET("/health", HealthCheck(), healthHandler)
```

选择标准很简单：影响全局的（日志、恢复）挂全局；要鉴权的（admin、写操作）挂分组；只对个别接口特殊的（某接口限流）挂单条。别把本应组级的鉴权挂成全局，会让公开接口也要求登录。

## 上下文传递：c.Set 与 c.Get

中间件经常要把判断结果传给后面的 handler，比如鉴权后把用户信息塞进 context。用 c.Set 写入、handler 用 c.Get 取出：

```go
// 鉴权中间件
func AuthRequired() gin.HandlerFunc {
	return func(c *gin.Context) {
		token := c.GetHeader("Authorization")
		if !isValid(token) {
			c.JSON(401, gin.H{"error": "未授权"})
			c.Abort() // 终止剩余 handler 和中间件
			return
		}
		// 把用户信息放进 context，后面的 handler 能取到
		c.Set("userID", int64(123))
		c.Next()
	}
}

// handler 里取
func myHandler(c *gin.Context) {
	uid := c.GetInt64("userID")
	_ = uid
	userID, exists := c.Get("userID") // 更通用的取法
	_ = userID
	_ = exists
}
```

c.Abort() 表示不再继续执行后面的中间件和 handler，但前面已经执行过的中间件代码（比如日志）仍会走完。和 c.Next() 对应，是一对"放行/拦截"开关。

c.Get 返回的永远是 any，用 c.GetInt64、c.GetString 这类有类型的 getter 更安全，取不到时返回零值。

## 常见中间件一：请求日志

```go
func Logger() gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		path := c.Request.URL.Path

		c.Next()

		latency := time.Since(start)
		status := c.Writer.Status()
		log.Printf("%s %s %d %v", c.Request.Method, path, status, latency)
	}
}
```

status 用 c.Writer.Status() 拿到，因为 handler 里实际写的状态码需要从 Writer 读。日志里带上 method、path、状态码、耗时，排查问题就有了第一步证据。

## 常见中间件二：panic 恢复

Gin 自带 Recovery() 中间件，panic 时不会让进程崩掉，而是返回 500。它做了几件事：捕捉 panic、打印堆栈、返回 500 响应。默认挂 r.Use 就是干这个：

```go
r.Use(gin.Recovery())
```

自己的业务中间件里如果还有可能 panic 的代码，仿照一份恢复逻辑即可。注意 Recovery 要用加在链路外层（先 Use），确保它处于洋葱的最外层，这样才能兜住内层所有 panic。

## 常见中间件三：CORS

跨域是前后端分离最常见的痛点。写一个允许所有来源的 CORS 中间件：

```go
func CORS() gin.HandlerFunc {
	return func(c *gin.Context) {
		c.Header("Access-Control-Allow-Origin", "*")
		c.Header("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS")
		c.Header("Access-Control-Allow-Headers", "Origin, Content-Type, Authorization")

		if c.Request.Method == "OPTIONS" {
			c.AbortWithStatus(204) // 预检请求直接返回，不进入业务
			return
		}
		c.Next()
	}
}
```

浏览器发跨域请求前会先发一个 OPTIONS 预检，用途是问服务器"我能不能这么干"。中间件在这个阶段直接返回 204 放行，后续真实请求才进 handler。

## 洋葱的执行顺序

理解了 Next 的语义，执行顺序自然清楚：请求按注册顺序进入外层中间件，c.Next() 处穿越到内层，直到 handler；响应再按相反顺序穿出来。给两个中间件加打印就能验证，这也是调试中间件问题的常用手段。

## 常见坑

第一个坑是中间件里忘了调 c.Next()。没调就是拦截，请求永远到不了 handler，接口全部返回空响应或超时。任何只是"经过"的中间件都必须记得放行。

第二个坑是 c.JSON 之后又调 c.Next()。已经写出去响应了再放行，属于语义混乱，多半是把错误分支的 Abort 写成了 Next，回看状态码会矛盾。

第三个坑是修改了 c.Request.Body 却忘了恢复。读取过 body 后 handler 里就空了，需要时先把 body 缓存再重放。

第四个坑是把全局中间件和分组中间件的作用范围搞混。全局会影响所有路由（包括健康检查、公开接口），鉴权这类要精确控制范围的应该挂在分组或单条上。
