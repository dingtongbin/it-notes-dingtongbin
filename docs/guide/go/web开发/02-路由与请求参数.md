# 路由与请求参数

接口建立在路由上，参数从请求里来。这一篇把 Gin 处理输入的常用手段过一遍：查询参数、路径参数、请求头、表单与原始 body，讲清楚每个来源该用哪个方法，以及常见的边界。

## 查询参数：query

GET 请求通常带 query，即 URL 问号后面的键值对。用 c.Query 取，不存在返回空串：

```go
r.GET("/users", func(c *gin.Context) {
	page := c.Query("page")      // 没传就是 ""

	// 需要带默认值或转数字时，用 DefaultQuery 和 Query 加转换
	pageStr := c.DefaultQuery("page", "1")
	pageNum, err := strconv.Atoi(pageStr)
	if err != nil {
		c.JSON(400, gin.H{"error": "page 必须是数字"})
		return
	}

	// 需要判断"有没有传"这个标记，用 GetQuery：
	// 第一个返回值是布尔，区分空串和未传
	if raw, ok := c.GetQuery("status"); ok {
		// ok 为 true 才说明 query 里真的带了 status 这个键
		_ = raw
	}
})
```

取 query 的三个方法区别要记清：c.Query 拿不到就返回空串，适合大多数场景；c.DefaultQuery 在空时给默认值，省一次判断；c.Query 的 Get 版返回布尔，能区分"传了空串"和"根本没传"这两种情况。

拦截空值并转数字是最常见的组合，正式代码里通常会抽成一个助手函数避免到处手写。

## 路径参数：param

路径参数用冒号声明，用 c.Param 读取，得到的总是字符串：

```go
r.GET("/users/:id/posts/:pid", func(c *gin.Context) {
	userID := c.Param("id")
	postID := c.Param("pid")
	c.JSON(200, gin.H{"user": userID, "post": postID})
})
```

路径参数和查询参数的分工是固定的：路径参数标识资源某个唯一实例（谁的帖子），查询参数表达筛选和分页（第几页、按什么排序）。用错的话 URL 会很难看，也不符合 REST 习惯。

## 请求头与 Cookie

```go
r.GET("/auth", func(c *gin.Context) {
	token := c.GetHeader("Authorization")  // 拿不到返回空串

	// 有时需要"有没有这个头"，用 Request.Header.Get 返回双值
	if v := c.Request.Header.Get("X-Request-Id"); v != "" {
		_ = v
	}

	cookie, err := c.Cookie("session")
	if err != nil {
		// 没这个 cookie 时返回错误
		_ = cookie
	}
})
```

c.GetHeader 是 c.Request.Header.Get 的简写，区别只在一个返回空串、一个返回空串加可判断。心跳中间件、鉴权中间件里读头的频率最高。

## 表单：form

带表单类型的内容，用 PostForm 读取。它不关心 body 是 x-www-form-urlencoded 还是 multipart，只要字段名对得上就能读：

```go
r.POST("/users", func(c *gin.Context) {
	name := c.PostForm("name")         // 字段不存在返回 ""
	age, _ := strconv.Atoi(c.PostForm("age"))

	// c.DefaultPostForm 支持默认值，适合可选字段
	remark := c.DefaultPostForm("remark", "无")

	c.JSON(200, gin.H{"name": name, "age": age, "remark": remark})
})
```

## 原始 body

需要自己解析非标准结构时，直接读 c.Request.Body。读之前建议先把 Content-Type 判断清楚，Gin 不会替你猜：

```go
r.POST("/raw", func(c *gin.Context) {
	data, err := io.ReadAll(c.Request.Body)
	if err != nil {
		c.JSON(400, gin.H{"error": err.Error()})
		return
	}
	c.JSON(200, gin.H{"got": string(data)})
})
```

io.ReadAll 会一次性把 body 全读进内存，超大 body 要限制大小，否则内存会爆。真实场景里大多数请求体是 JSON，直接走下一章的 ShouldBindJSON，不需要手动读。

## 取 header 的小工具

调试时想看请求全貌，Header 里用 Get 拿单个，用步进遍历拿全部：

```go
r.GET("/dump", func(c *gin.Context) {
	// 只拿到第一个值，适合 Authorization 这类单值头
	v := c.GetHeader("Accept-Language")

	// c.Request.Header.Values 取同名的所有值，例如 Accept 可能有多个
	vals := c.Request.Header.Values("Accept")
	_ = v
	_ = vals
})
```

## 一个完整的查询接口示例

把前面串起来，写一个"按名字过滤并分页"的接口：

```go
r.GET("/api/v1/hosts", func(c *gin.Context) {
	var (
		page int
		size int
	)
	if raw := c.Query("page"); raw != "" {
		page, _ = strconv.Atoi(raw)
	}
	if raw := c.Query("size"); raw != "" {
		size, _ = strconv.Atoi(raw)
	}
	if page < 1 {
		page = 1
	}
	if size < 1 || size > 100 {
		size = 20 // size 设上限，防止恶意大页
	}
	name := c.Query("name")

	c.JSON(200, gin.H{
		"page":  page,
		"size":  size,
		"name":  name,
		"items": []Host{}, // 占位，下一章接数据库后填
	})
})
```

size 上限是一种防御式编程：用户传 size=1000000 时直接限制在 100，避免一次返回海量数据压垮接口和数据库。

## 常见坑

第一个坑是 c.Query 返回的空串和真的空值分不清。需要区分时用 c.Query 的 Get 版本拿布尔标记，别用 len(str) == 0 去猜。

第二个坑是路径参数的类型。c.Param 永远返回字符串，拿去做运算前必须先转，漏了转换会在运行时才暴露。

第三个坑是 GET 也用了 ShouldBind 想绑定 form，结果绑不到值。GET 的 body 几乎总是空的，表单要 POST，query 要用 Query 相关方法。

第四个坑是直接读 c.Request.Body 没有限制大小。确保 body 可控，真实项目用 ShouldBind 或加 MaxBytesReader，避免被大 body 打到内存告警。
