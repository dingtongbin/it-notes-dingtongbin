# 时序数据建模

agent 和探活器产出指标，落盘成了瓶颈。这一节用 MySQL 起步做时序存储，先讲清建模：时序数据有什么特征、宽表为什么是死路、标签怎么设计。数据模型定错了，后面查询和告警全都跟着难受。

## 时序数据的五个特征，五个设计决策

时序数据不是"带时间戳的普通数据"，它的每个特征都直接推出一条设计约束：

| 特征 | 含义 | 推出的设计决策 |
|---|---|---|
| append-only | 只追加，从不改历史 | 不需要 UPDATE 路径；主键 (series_id, ts) 顺带防重 |
| 不可变 | 写进去就没人动它 | 无需乐观锁/版本号；批量写大胆重试，幂等靠主键 |
| 近热远冷 | 最近 24h 被疯狂查询，上月数据偶尔看 | 按天分区，冷数据整分区 DROP，热数据留缓冲池 |
| 写多读少 | 写入是常态洪峰，查询是偶发尖峰 | 所有优化向写路径倾斜：攒批、异步、失败退避 |
| 时间局部性 | 查询几乎总带时间范围 | 索引 (series_id, ts)，一次磁盘顺序读拿下整段曲线 |

## 存储选型

| 存储 | 原理一句话 | 适用规模 | 运维成本 |
|---|---|---|---|
| MySQL 分区表 | InnoDB 表 + 按天 RANGE 分区 | 日增千万点内 | 低（复用现有 DB） |
| TimescaleDB | Postgres 扩展，自动分块 + 自动 rollup | 中 | 中（要有 PG 经验） |
| InfluxDB | TSM 树 + 倒排索引 | 中大（2.x Flux 语言门槛高） | 中 |
| VictoriaMetrics | LSM 式合并 + 倒排索引，单二进制 | 大 | 低（资源占用出名的省） |
| Prometheus 本地 TSDB | head chunk + block 后台压实 | 单机抓取、短期保留 | 低（与 Prometheus 一体） |

gomon 从 MySQL 起步的理由：团队已经在用、备份恢复体系现成、日增千万点内完全扛得住。等出现换专业库的信号再迁 VictoriaMetrics——数据模型不变，换的是 DataSource 实现。

## MySQL 表设计

### 窄表优于宽表

宽表（每个指标一列：host, ts, cpu, mem, disk...）看着省行数，实际是死路：新增指标要 ALTER TABLE 锁表；不同机器指标集合不同，表越加越稀疏。窄表一行一个点，加指标 = 加数据不加结构：

```sql
-- 序列表：metric + tags 组合的唯一编号（"序列"= 同一指标同一维度组合）
CREATE TABLE series (
    id     BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    metric VARCHAR(64)  NOT NULL,   -- 指标名，如 cpu.percent
    tags   VARCHAR(255) NOT NULL,   -- 规范化标签串，如 mount=/data|os=linux
    UNIQUE KEY uk_metric_tags (metric, tags)
) ENGINE=InnoDB;

-- 数据点表：窄表，一行一个点；series 数靠 series 表控制
CREATE TABLE metric_points (
    series_id BIGINT UNSIGNED NOT NULL,
    ts        DATETIME(6)     NOT NULL,  -- 统一存 UTC
    val       DOUBLE          NOT NULL,
    PRIMARY KEY (series_id, ts)          -- 顺序不能反
) ENGINE=InnoDB;
```

### 标签建模：JSON 列 vs 序列表

| 方案 | 写入 | 查询 | 基数控制 |
|---|---|---|---|
| JSON 列存 tags | 简单 | 按标签过滤要走 JSON 函数，索引难用 | 无感知，series 数暗中爆炸 |
| 序列表 + series_id（gomon 选它） | 多一步查/建 series | 先按 metric+tags 查 id，再按 id 查点 | series 表行数就是基数，一眼可见 |

```go
// store/series.go
package store

import (
    "context"
    "database/sql"
    "maps"
    "slices"
    "strings"
    "sync"
)

// SeriesCache metric+tags → id 的进程内缓存。
// 没有它，每个点都要先查一次 series 表——写路径查询数翻倍
type SeriesCache struct {
    db *sql.DB
    mu sync.RWMutex
    m  map[string]uint64 // key: "cpu.percent|mount=/data"
}

func (c *SeriesCache) ID(ctx context.Context, name string, tags map[string]string) (uint64, error) {
    key := seriesKey(name, tags)
    c.mu.RLock()
    id, ok := c.m[key]
    c.mu.RUnlock()
    if ok {
        return id, nil
    }
    // 缓存未命中：INSERT IGNORE 顺带完成注册（已存在则无副作用），再取回 id
    if _, err := c.db.ExecContext(ctx,
        "INSERT IGNORE INTO series (metric, tags) VALUES (?, ?)", name, key); err != nil {
        return 0, err
    }
    var nid uint64
    if err := c.db.QueryRowContext(ctx,
        "SELECT id FROM series WHERE metric = ? AND tags = ?", name, key).Scan(&nid); err != nil {
        return 0, err
    }
    c.mu.Lock()
    c.m[key] = nid
    c.mu.Unlock()
    return nid, nil
}

// seriesKey 标签串规范化：map 无序，必须排序后拼接，
// 否则同一组标签两次上报会注册出两个 series，曲线断成两截
func seriesKey(name string, tags map[string]string) string {
    if len(tags) == 0 {
        return name
    }
    var b strings.Builder
    b.WriteString(name)
    for _, k := range slices.Sorted(maps.Keys(tags)) {
        b.WriteByte('|')
        b.WriteString(k)
        b.WriteByte('=')
        b.WriteString(tags[k])
    }
    return b.String()
}
```

seriesKey 是隐藏的坑：map 迭代无序，同一组标签必须排序后再拼接，否则每次上报都生成一个不同的 key，注册出无数个 series，曲线断成两截。

## 常见坑

第一个坑是高基数标签打爆 series 数：tags 里混进 pid=1234、request_id 这类高基数字段，进程一重启就是一个新 series，一天注册出几十万行，series 表和缓存双吃瘪，查询聚合全是碎片。规矩：tags 只允许低基数字段（host/mount/device/method），高基数维度单独建表分析，不进时序主链路。

第二个坑是无界批量缓冲 OOM：DB 故障半小时，"先在内存里攒着"的缓冲默默吃掉几个 GB。必须有 maxBuf + 丢老保新 + 丢弃计数三件套，丢得明明白白比 OOM 强。

第三个坑是标签拼接顺序不稳定：map 无序，每次上报拼接出不同 key，series 表无限膨胀。用 sorts 排序后再拼接，或干脆用哈希序列化。

第四个坑是时间戳时区混乱：agent 打本地时间戳、server 存 DATETIME、前端按又一时区解析，曲线错 8 小时。铁律：存储与传输统一 UTC，只在展示层转本地时区。

第五个坑是主键顺序写反：(ts, series_id) 做主键，同一序列的点在 B+ 树上按时间全局散开，序列查询变成随机 IO。必须 (series_id, ts)：同序列的点物理相邻，范围查询一次顺序读。
