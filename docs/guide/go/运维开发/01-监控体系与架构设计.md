# 监控体系与架构设计

前面几章把零件备齐了：database/sql 与 GORM 管数据、net/http 与 gRPC 管通信、viper/slog 管工程骨架。从这一章开始，把这些零件组装成一台完整的机器：一个类 Zabbix 的监控系统，agent 采集、server 调度存储告警、proxy 跨机房缓冲。本章不写代码，只画图纸：监控分几层、Zabbix 与 Prometheus 为什么长成那样、模块怎么拆、容量怎么算。后面所有章节都按这张图纸施工。

## 监控分层金字塔

从机房的物理世界到业务数字，监控对象天然分六层。越往下离硬件越近、故障越致命；越往上离用户越近、越能回答"业务是否受损"。任何监控系统，本质上都在回答"覆盖哪几层、每层怎么采"。

```
                ┌────────────┐
                │ 6 业务层    │  下单量、支付成功率、登录失败数
             ┌──┴────────────┴──┐
             │ 5 应用层          │  QPS、P99 时延、5xx 率、GC
          ┌──┴──────────────────┴──┐
          │ 4 中间件层              │  MySQL、Redis、NATS、Nginx
       ┌──┴────────────────────────┴──┐
       │ 3 网络层                       │  丢包、RTT、端口可达、证书
    ┌──┴────────────────────────────────┴──┐
    │ 2 系统层                                │  CPU、内存、磁盘、进程
 ┌──┴──────────────────────────────────────────┴──┐
 │ 1 基础设施层                                      │  交换机、UPS、温湿度、IPMI
 └──────────────────────────────────────────────────┘
```

| 层 | 监控对象举例 | 采集方式 |
|---|---|---|
| 基础设施 | 交换机端口流量、防火墙会话数、UPS 电量、机房温湿度、虚拟化宿主机 | SNMP / IPMI |
| 系统 | CPU、内存、磁盘空间与 IO、网络流量、负载、关键进程 | agent 白盒采集 |
| 网络 | ping 丢包率与 RTT、TCP 端口可达、HTTPS 证书有效期、DNS 解析耗时 | 拨测（blackbox） |
| 中间件 | MySQL 连接数与慢查询、Redis 内存与命中率、NATS 积压、Nginx 状态 | agent 内置模块 |
| 应用 | HTTP QPS、错误率、P99 时延、goroutine 数、panic 计数 | 埋点 + pprof |
| 业务 | 订单量、支付成功率、库存水位、注册量 | 业务 API / 日志 |

分层的价值在告警定位。支付成功率掉下来，顺着金字塔往下查：业务红灯、应用 5xx 升高、MySQL 慢查询、磁盘 IO 打满。每一层都有数据，才能从"业务出事了"三分钟收敛到"某台机器某块盘"；缺一层，链路就断在一次拍脑袋上。

## 好指标的方法论：USE / RED / Golden Signals

采集不是越多越好。每加一个指标都是存储、告警规则、认知成本的三重买单。三个经过验证的框架，用来回答"到底该采什么"。

### USE：给资源找指标

Brendan Gregg 的 USE 方法：任何资源问三件事——Utilization（利用率）、Saturation（饱和度）、Errors（错误）。饱和度最容易被忽略也最能预警：利用率 100% 说明已经出事，饱和度上升说明正在排队、马上出事。

| 资源 | 利用率 | 饱和度 | 错误 |
|---|---|---|---|
| CPU | cpu.percent | load 除以核数、runnable 队列 | - |
| 内存 | used / total | swap 使用量、OOM 次数 | - |
| 磁盘 | busy 时间占比 | iowait、IO 队列深度 | IO 错误数 |
| 网络 | 带宽 / 端口速率 | 丢包率、重传率 | CRC 错误 |

### RED：给服务找指标

Rate（请求速率）、Errors（错误率）、Duration（时延分布）。每个对外接口至少这三个。P99 比 P50 重要——平均值会撒谎：100 个请求里 99 个 10ms、1 个 5s，平均 59ms 看似健康，其实已经有一个用户的体验是灾难。

### Four Golden Signals

Google SRE 的四件套：延迟、流量、错误、饱和度。相当于 USE 与 RED 的合并版，适合当巡检大盘的第一屏。

### 反例：采了也白采的指标

常量当指标：CPU 核数、OS 版本上报一万次也是同一个值，它们是资产元数据，不是时序数据。

无维度的总量：只存"全网 QPS"不带接口标签，出错时无法下钻定位。

从不告警也从不看的图：存了三年没人打开，纯烧磁盘。

平均值替代分布：只存 avg 丢掉长尾，SLA 违约了都发现不了。

采样过密的水位类指标：磁盘空间变化以小时计，10 秒采一次毫无信息量，白写 300 倍数据。

## Zabbix 架构深剖

Zabbix 2001 年发布，20 多年迭代覆盖了 SNMP、agent、拨测、JMX 几乎所有采集方式，是传统机房监控的事实标准。gomon 整体就是它的简化复刻，先看懂它。

### 组件与数据流

```
                     ┌───────────────┐
                     │ Web Frontend  │  PHP：配置、展示
                     └───────┬───────┘
                             │ 读写配置 / 读数据
   主动检查                  │
   agent ──► 10051 ──► ┌────▼────────────┐      ┌──────────┐
   （agent 主动连上来送） │  Zabbix Server │ ───► │ Database │
                        │ poller/trapper │      │ MySQL 等 │
                        │ alerter/timer  │      └──────────┘
                        └──┬──────────┬───┘
      被动检查              │          │ 写历史/触发器/事件
      server ──► 10050 ────┘          ▼
      （server 连过去轮询）      ┌──────────┐
                               │ Proxy    │ 分机房采集缓冲，断网续传
                               └────┬─────┘
                                    │
                          agent / SNMP / 拨测目标
```

### 主动检查 vs 被动检查：端口语义

| 维度 | 被动检查 | 主动检查 |
|---|---|---|
| 谁发起 | server 连 agent 的 10050 端口 | agent 连 server 的 10051 端口 |
| server 端进程 | poller | trapper |
| 调度 | server 的轮询表驱动 | agent 自己按 interval 定时 |
| 适合 | 小规模、server 可直连所有 agent | 大规模、NAT 后、防火墙只出不进 |
| 失联判定 | 轮询失败立刻知道 | 靠 server 的"无数据超时"（nodata）间接判断 |

两端口语义最容易混：10050 是 agent 的监听端口（被 server 连），10051 是 server 的监听端口（被 agent 连）。gomon 的对应设计：主动走 gRPC 流，被动走 TCP 拉取，调度器编排被动侧。

### 进程模型与公认瓶颈

Zabbix server 是多进程架构：父进程 fork 出一组工作进程。

| 进程 | 职责 |
|---|---|
| poller | 轮询被动 agent、SNMP、拨测 |
| trapper | 接收主动上报（10051） |
| alerter | 发送通知（邮件/短信/webhook） |
| timer | 维护期、告警升级的定时触发 |
| housekeeper | 清理过期历史数据 |

两个公认的瓶颈，gomon 都要正面回答：

数据库：history 表按点写入，10 万个 item × 30s 间隔就是 3000+ 行/秒持续写；housekeeper 大批量 DELETE 还会打穿 buffer pool 缓存。gomon 对策：按时间分区，过期直接 DROP 整个分区。

poller 数量：被动轮询吞吐受 poller 进程数限制，规模一大轮询周期被拉长，数据延迟放大。gomon 对策：goroutine 池替代进程池，单机轻松上万并发探测。

### 概念链：item 到 trigger 到 event 到 action 到 escalation

```
item        采集项：system.cpu.util，每 10s 取一次
  ↓
trigger     触发器（表达式）：last(/web01/system.cpu.util) > 0.9
            状态在 OK 与 PROBLEM 之间跳变
  ↓
event       每次状态跳变产生一个事件
  ↓
action      动作：发通知 / 远程执行命令 / 调 webhook
  ↓
escalation  升级：30 分钟无人确认，自动打电话给二线
```

这条链是所有监控系统的通用范式。gomon 的告警引擎原样照搬：表达式 DSL 扮演 trigger，状态机管理跳变与防抖，通知器带重试和升级链。

## Prometheus 架构深剖

### 组件与 pull 模型

```
┌──────────┐  pull /metrics  ┌────────────┐  告警规则   ┌─────────────┐
│ Exporter │◄────────────────│ Prometheus │──────────►│ Alertmanager │
│ node:9100│                 │ 采样+TSDB  │            │ 分组/去重/静默 │
└──────────┘                 │  PromQL    │            └──────┬──────┘
┌──────────┐                 └─────┬──────┘                   ▼
│  短任务   │──push──►Pushgateway◄──pull──┘              邮件/电话/webhook
└──────────┘        （中转站）      │ 联邦 / 远程读写
                                   ▼
                        长期存储（Thanos / VictoriaMetrics）
```

四个关键设计：

pull：Prometheus 周期性 HTTP 抓取目标的 /metrics 文本，目标端只要暴露 HTTP 就行。

exporter 生态：应用自己暴露 /metrics（Go 程序引 promhttp 三行代码），第三方装对应 exporter。

本地 TSDB：单机时序库，默认只留 15 天——哲学是"近期数据本地查，长期数据交给远端"。

Alertmanager 职责分离：Prometheus 只评估规则发 alert；分组、去重、静默、路由、升级全在 Alertmanager。"判定"与"送达"解耦，gomon 告警引擎直接借鉴这个分层。

### pull 与 push：一场值得听完的辩论

| 维度 | pull（Prometheus） | push（Zabbix 主动 / gomon 流式） |
|---|---|---|
| NAT / 防火墙穿透 | 难，目标必须可达 | 天然友好，agent 只出站 |
| 短任务（跑完就退） | 要 Pushgateway 中转 | 直接推完退出 |
| 时钟依赖 | server 打时间戳，agent 时钟无关 | agent 打时间戳，漂移会污染数据 |
| 故障语义 | 抓取失败 = 目标挂或网络断，有歧义 | 停推 = agent 挂或网络断，同样有歧义 |
| 传输效率 | 每次全量拉 | 可攒批增量推，省带宽 |
| 谁证明谁活着 | 抓取循环证明 server 活着 | agent 心跳证明 agent 活着 |

结论不是谁赢：云原生内网环境 pull 生态无敌；跨机房、NAT 后、边缘节点 push 更现实。gomon 选 push 为主（gRPC 流）+ 被动拉取兜底（调度器），两头都占。

## Zabbix 与 Prometheus：怎么选

| 维度 | Zabbix | Prometheus |
|---|---|---|
| 数据模型 | 主机为中心：host 到 item | 指标为中心：metric 加标签维度 |
| SNMP / 拨测 | 原生完整，开箱即用 | snmp_exporter / blackbox_exporter，配置繁琐 |
| 自动发现 | 网络发现、LLD 自动建监控项 | 服务发现依赖云原生环境 |
| 存储 | 关系型 DB，超大集群是灾难 | 本地 TSDB 15 天，长期靠外接 |
| 查询分析 | SQL 受限、前端图表老 | PromQL + Grafana，分析能力强一档 |
| 告警 | 触发器与升级机制成熟 | 规则简单，复杂路由交给 Alertmanager |
| 学习曲线 | Web UI 表单几十个字段 | YAML + PromQL，程序员友好 |
| 适合团队 | 传统 IDC、网络设备多、专职运维 | K8s / 微服务、开发自运维 |

一句话：机房与交换机选 Zabbix，容器与微服务选 Prometheus。gomon 面向前者形态（主机为中心 + SNMP + 拨测），但用 Go 与流式协议把 Zabbix 最痛的 DB 写入与 poller 瓶颈重做一遍。

## 容量估算实战

架构不是画完就完。SRE 的习惯是给每个设计配一个数：目标规模 1000 台主机 × 50 指标 × 10s 间隔。所有算式展开，换你自己的规模时照套。

### 写入速率

```
points/s = 1000 台 × 50 指标 ÷ 10s = 5000
```

### 网络带宽

proto 编码后每点约 40 字节（一个批次共享 agent_id 与元数据，点内是指标名引用 + 值 + 时间戳 + 少量标签；gRPC 头部压缩后更小，取保守值）：

```
5000 points/s × 40 B ≈ 200 KB/s ≈ 1.6 Mbps
```

千兆内网可忽略。但攒批会造成突发：5 秒攒一批，就是每 5 秒约 1MB 的瞬时脉冲，网卡的 burst 缓冲要能吃下。

### 原始存储（保留 7 天）

InnoDB 每行实际开销按 80 B 估（有效载荷约 24 B：host_id 4 + metric_id 4 + ts 8 + value 8，其余是行头、页开销、二级索引——估算时必须给实测值翻倍的余量）：

```
日增 = 5000 × 80 B × 86400 ≈ 34.5 GB/天
7 天原始 ≈ 240 GB
```

### 降采样后（保留 90 天）

10s 原始聚合成 5 分钟一行，存 min/avg/max/count 四个值，行宽按 120 B：

```
降采样写入 = 5000 ÷ 30 ≈ 167 行/s
日增 = 167 × 120 B × 86400 ≈ 1.7 GB/天
90 天 ≈ 155 GB
```

### 总账与 DB 写入压力

```
总存储 = 240 GB（原始 7 天）+ 155 GB（降采样 90 天）≈ 400 GB
```

单实例 MySQL + 1TB NVMe 盘可承载——这就是"MySQL 起步"的底气。写入压力的两种做法：

| 写法 | DB 压力 | 后果 |
|---|---|---|
| 逐条 INSERT | 5000 QPS、5000 事务/秒 | binlog 与刷盘打满，主从延迟飙升 |
| 攒 500 条一批 | 10 QPS（每批一个事务） | 连接占用 10 个，轻松 |

结论：批量写是必需品不是优化项。

### 换算成部署要求

server 单进程可扛：Go 单机每秒解析并落盘 5000 个点远不到瓶颈。

MySQL 独立实例、NVMe 盘，innodb_flush_log_at_trx_commit 设 2（监控数据丢 1 秒可接受，换吞吐）。

涨到 10000 台时写入 50000 点/秒，MySQL 单机到顶——存储层接口就是为届时切 VictoriaMetrics 留的门。

## 数据流全链路：每一环都可能丢数据

```
采集 → 传输 → 缓冲 → 存储 → 规则计算 → 告警 → 通知 → 可视化
```

监控系统的可靠性等于每一环"丢了什么、能不能发现"的乘积。逐环审计：

| 环节 | 会丢什么 | 发现手段（gomon 的设计） |
|---|---|---|
| 采集 | collector 阻塞或 panic，该指标缺点 | 每轮上报采集成败计数 |
| 传输 | 断网丢整批 | 批次 seq 单调递增，server 检测缺口并计数 |
| 缓冲 | 有界队列满，按策略丢旧 | 丢弃计数随批上报，曲线图可见 |
| 存储 | DB 抖动写失败 | 写入失败计数 + 失败批落盘重放 |
| 规则计算 | 数据缺口期间不触发告警 | 缺口窗口内保持上一状态，恢复后重新求值 |
| 告警 | 通知渠道故障 | 多渠道重试 + 升级链兜底 |
| 可视化 | 断点被连线掩盖 | 前端显式渲染缺口而非连成直线 |

最后一问：谁监控监控？gomon-server 自己也装一个 gomon-agent 被自己监控（自举），再用一条独立的裸 ICMP 拨测看住整条链路。这个主题在高可用那一章展开。

## 常见坑

第一个坑是一上来就自研时序库：压缩、LSM、降采样每一个都是独立工程，没上线先耗半年。MySQL 分区表跑到千台规模再谈更换，本章的算式就是底气。

第二个坑是指标不带标签维度：只存 disk.used=93.5，不知道哪台机哪块盘，聚合和告警都无从下手。维度设计在采集端就要定死，Metric 结构里的 tags 字段为此而设。

第三个坑是只采集不告警等于没监控：数据躺在库里没人看，故障还是靠用户打电话发现。每个指标要么有告警规则，要么明确"只做趋势分析"。

第四个坑是监控系统自身单点：server 挂了全部失明，而它挂的时候恰好是你最需要监控的时候。谁监控监控必须在架构图里有答案。

第五个坑是容量靠感觉：不做乘法就上线，三个月后监控库先于业务库挂掉。本章的算式，换上自己的数字算一遍再开工。

第六个坑是告警阈值一刀切：所有机器同一个 CPU 阈值，跑批任务的机器天天误报，告警疲劳之后真告警也被顺手静音。阈值要么按角色分组，要么用同环比。
