# 轮询调度器

agent 白盒上报、探活器拨测解决了"怎么采"。但 server 还欠一个核心问题——何时采。这一节实现轮询调度器：最小堆给 1 万个检查项排期，按类型隔离的 worker 池执行，慢探活绝不拖垮快任务。它就是 Zabbix poller 的 Go 版。

## 问题定义

把需求钉死再动手：

规模：1 万个检查项（ICMP/TCP/HTTP/SNMP/agent 拉取），interval 从 5 秒到 5 分钟不等，各自带 timeout。

准时：一个 60s 周期的检查项，实际执行时刻与应执行时刻的差值（调度延迟）必须可观测、可告警。

隔离：一次 SNMP Walk 要 30 秒，绝不能让 ICMP 这种毫秒级探活在它后面排队。

有界：任何队列都要有容量上限，满了有明确策略而不是无限堆积。

可退出：ctx 取消后，在途任务执行完、堆里剩余任务状态落库，进程干净退出。

数据从哪来：检查项配置存在 DB（hosts 表 + 模板），启动时加载，运行期通过 SetChecks 热更新（增删主机不用重启 server）。执行体复用前面写的探活函数与被动模式拉取。

## 方案对比：三种定时模型

每任务一个 goroutine + time.Sleep：最直观，但有三个量化的坑。内存上，goroutine 起步 2KB 栈（见 go 基础语法的 goroutine 篇），1 万个约 20MB——其实扛得住；真正致命的是惊群：人工配置的 interval 天然整点对齐（几乎全是 60s），每个整点后 8000 个 goroutine 同时醒来，瞬时负载尖刺直接把探活超时打爆，产出一片假 DOWN；还有漂移：Sleep(60s) + 执行 2s = 62s 周期，越跑越慢，永远回不到整点。

时间轮：环形槽数组，指针每 tick 前进一格，槽里挂"恰好还有这么多 tick 到期"的任务；超过一圈的记 round，指针每经过一圈 round 减一，归零才执行。

```
 60 个槽，指针每秒前进一格（一个 tick）：

    ┌────┬────┬────┬────┬─ ─ ─┬────┐
    │ 0  │ 1  │ 2  │ 3  │ ... │ 59 │   槽 i 挂"还有 i 秒到期"的任务
    └────┴────┴────┴────┴─ ─ ─┴────┘
               ▲
               └── 指针走到本槽：槽内任务全部执行，执行后清空

 超过 60 秒的任务：记 round=N 放入 (now+i) % 60 号槽，指针每经过一次 round--，归零才执行。
 加任务 O(1)、惰性删除 O(1)——百万级任务增删都是常数时间，Netty/Kafka 内部全是它。
```

最小堆：堆顶永远是最早到期的任务，调度器睡到堆顶时刻即可。

| 方案 | 增删复杂度 | 准时性 | 代码量 | 适用规模 |
|---|---|---|---|---|
| 每任务 goroutine | 无队列 | 漂移 + 惊群 | 最少 | < 1000 项、interval 分散 |
| 时间轮 | O(1) | 受 tick 粒度限制 | 大（round/多级） | 10 万+ 项、网络框架 |
| 最小堆 | O(log n) | 精确（事件驱动） | 小（container/heap） | gomon 选它 |

结论：1 万级规模，堆的单锁竞争完全无感（每次操作微秒级），代码量只有时间轮的三分之一；等检查项上到百万级（多机房聚合调度）再换时间轮。

## 检查项模型与调度粒度

```go
// scheduler/check.go
package scheduler

import "time"

// Check 一个检查项的调度视图：调度器只关心"何时派发给谁"，
// 怎么执行是探活函数和被动模式的事
type Check struct {
    ID       int64         `json:"id"`
    Type     string        `json:"type"`     // icmp / tcp / http / snmp / agent
    Target   string        `json:"target"`   // IP / URL / agent 地址
    Interval time.Duration `json:"interval"` // 轮询周期
    Timeout  time.Duration `json:"timeout"`  // 单次执行超时
    NextRun  time.Time     `json:"-"`        // 下次应执行时刻——只活在内存，绝不落库
}
```

调度粒度的取舍：监控域里 interval 最小 5 秒，人对指标的感知粒度也是秒级——亚秒级调度精度毫无价值，只增加唤醒次数。堆方案是纯事件驱动（睡到下一个到期点），天然没有 tick；如果想省事也可以用 1 秒 ticker 扫堆顶，代码更短，代价是最多 1 秒的额外延迟。两者都成立，gomon 选事件驱动。

NextRun 只活在内存：经过序列化变成 Unix 时间戳，Go 的单调时钟语义就丢了，NTP 拨回后任务会集体沉默。

## 最小堆调度器（本章核心）

### 堆实现

标准库 container/heap 只提供框架，五个方法自己写：

```go
// scheduler/heap.go
package scheduler

import "container/heap"

// checkHeap 按 NextRun 排序的最小堆：堆顶 = 最早该执行的任务
type checkHeap []*Check

func (h checkHeap) Len() int           { return len(h) }
func (h checkHeap) Less(i, j int) bool { return h[i].NextRun.Before(h[j].NextRun) }
func (h checkHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }

func (h *checkHeap) Push(x any) { *h = append(*h, x.(*Check)) }

func (h *checkHeap) Pop() any {
    old := *h
    n := len(old)
    c := old[n-1]
    old[n-1] = nil // 置 nil：防指针悬挂导致 Check 无法被 GC
    *h = old[:n-1]
    return c
}
```

### 调度主循环

```go
// scheduler/scheduler.go
package scheduler

import (
    "context"
    "log/slog"
    "sync"
    "time"

    "container/heap"
)

type job struct {
    check *Check
    due   time.Time // 应执行时刻，用于统计调度延迟
}

type Scheduler struct {
    mu      sync.Mutex         // 保护 heap：主循环、SetChecks、指标读取三方都会碰
    heap    checkHeap
    pools   map[string]*Pool   // 按探活类型隔离的执行池
    updates chan []*Check      // 配置热更新入口
    stats   Stats
}

func New(pools map[string]*Pool) *Scheduler {
    return &Scheduler{
        pools:   pools,
        updates: make(chan []*Check, 1), // 容量 1：多次热更新排队不堆积，旧的被新的覆盖
    }
}

// SetChecks 全量替换检查项（增删主机走这里）。非阻塞：调度器忙不过来时旧配置继续跑
func (s *Scheduler) SetChecks(checks []*Check) {
    select {
    case s.updates <- checks:
    default: // 上一批还没消费：丢弃旧批次，留最新——配置同步永远以最新为准
        select {
        case <-s.updates:
        default:
        }
        s.updates <- checks
    }
}

// Run 调度主循环：睡到下一个到期点 → 取出到期任务 → 派发 → 压回堆
func (s *Scheduler) Run(ctx context.Context) error {
    timer := time.NewTimer(time.Hour)
    defer timer.Stop()
    for {
        // 每轮循环先看堆顶，把 timer 重置到下一个到期点——防止空转 busy-loop 的关键：
        // 没有任务时长睡等待新配置，有任务时精确睡到到期
        s.mu.Lock()
        var next time.Time
        if len(s.heap) > 0 {
            next = s.heap[0].NextRun
        }
        s.mu.Unlock()

        if next.IsZero() {
            timer.Reset(time.Hour) // 空堆：长睡，等 updates 唤醒
        } else if d := time.Until(next); d > 0 {
            timer.Reset(d)
        } else {
            timer.Reset(time.Millisecond) // 已过期（比如刚从热更新塞进来）：立即处理
        }

        select {
        case <-ctx.Done():
            return nil // 在途任务由各 Pool 的 Stop 负责排空
        case checks := <-s.updates:
            now := time.Now()
            s.mu.Lock()
            s.heap = s.heap[:0] // 全量替换
            for _, c := range checks {
                if c.Interval < time.Second {
                    c.Interval = time.Second // 兜底：防 0 值配置把调度器拖进热循环
                }
                // 首次排期加随机抖动：打散整点对齐，避免惊群
                c.NextRun = now.Add(c.Interval + time.Duration(randN(int64(c.Interval/10))))
                heap.Push(&s.heap, c)
            }
            s.mu.Unlock()
            slog.Info("检查项已加载", "count", len(checks))
        case <-timer.C:
            now := time.Now()
            s.mu.Lock()
            var due []*Check
            for len(s.heap) > 0 && !s.heap[0].NextRun.After(now) {
                due = append(due, heap.Pop(&s.heap).(*Check)) // 一次取出全部到期项
            }
            s.mu.Unlock()
            for _, c := range due {
                s.dispatch(c, now)
            }
        }
    }
}

// dispatch 投递给对应类型的池，并重排下一次运行。
// 投递用 try-send：池队列满就跳过本轮——调度主循环在任何情况下都不允许阻塞
func (s *Scheduler) dispatch(c *Check, due time.Time) {
    s.stats.ObserveLag(time.Since(due)) // 调度延迟：从"该跑"到"真正派发"

    if pool, ok := s.pools[c.Type]; ok {
        select {
        case pool.jobs <- job{check: c, due: due}:
        default:
            s.stats.skipped.Add(1) // 队列满：跳过本轮
            slog.Warn("池队列已满，跳过本轮", "type", c.Type, "check", c.ID)
        }
    } else {
        slog.Error("未注册的检查类型", "type", c.Type)
    }
    // 无论投递成败，NextRun 一律从"现在"重新起算：跳过的不追赶
    s.mu.Lock()
    c.NextRun = time.Now().Add(c.Interval)
    heap.Push(&s.heap, c)
    s.mu.Unlock()
}

func randN(n int64) int64 { // 简单抖动：n <= 0 时返回 0
    if n <= 0 {
        return 0
    }
    return time.Now().UnixNano() % n
}
```

设计要点：dispatch 不等执行结果。执行慢是池子的事，调度循环只负责"准时派发 + 重排"，所以慢探活再慢也拖不乱其他检查项的节拍。SetChecks 用容量 1 的有界通道，热更新风暴时只保留最新一批，旧配置继续跑，绝不堆积。

## 常见坑

第一个坑是时钟回拨把 NextRun 打乱：NTP 校正把墙钟拨回 10 分钟，堆里所有 NextRun 都"还没到"，任务集体沉默。Go 的 time.Now() 自带单调时钟，进程内用 Before/After 比较不受影响；但 NextRun 一旦经过 JSON/DB 序列化变成 Unix 时间戳，单调性就丢了。原则：NextRun 只活在内存，重启后从 now + Interval + 抖动重建。

第二个坑是堆被并发读写：调度循环 push/pop，管理接口想看"下一个到期任务"直接读 heap[0]——data race，-race 一跑一个准。所有堆操作必须过同一把锁，锁粒度就是"整个堆一把"，10 万级任务下足够。

第三个坑是整点对齐惊群：全部 interval=60s 的检查项首轮 NextRun 同毫秒到期，每个整点一次小雪崩。加载时加随机抖动打散。

第四个坑是追赶风暴：慢任务恢复后想把"欠的轮次"补回来——100 个积压连续派发再次打满池子。跳过就是跳过：NextRun 从 now 起算，绝不回头追历史。
