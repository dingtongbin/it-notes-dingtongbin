# 韧性能力：超时、重试与故障注入

微服务链条上，任何一个下游慢或挂都会拖累上游。Istio 让这些韧性策略集中到配置里，不改业务。这一篇讲超时、重试、故障注入，以及它们各自解决什么问题。

## 超时：上游与下游的契约

调用下游如果一直不返回，就会堆积占住上游的资源。给每个调用设超时是从根上防住"慢调用拖垮"：

```yaml
spec:
  hosts:
    - myservice
  http:
    - route:
        - destination: { host: myservice }
      timeout: 3s          # 3 秒没返回就放弃
```

设在 VirtualService 的路由上，超时后按策略走失败或重试。

## 重试：对瞬时失败的补偿

短暂抖动、瞬时错误，重试一次往往就成功了。显式配重试：

```yaml
      retries:
        attempts: 3          # 最多重试 3 次
        retryOn: connect-failure,5xx   # 哪些错误才重试
```

注意：重试适合幂等请求（GET 等），对非幂等的 POST 要谨慎，配错了副作用会被放大。

## 熔断：别把故障倒给后端的健康实例

重试和超时之外，熔断防止"全链路雪崩"。当后端某个实例连续失败，把它临时摘出流量，让其他健康实例继续服务：

```yaml
spec:
  host: myservice
  trafficPolicy:
    outlierDetection:
      consecutive5xxErrors: 5   # 连续 5 次 5xx
      interval: 30s             # 判定窗口
      baseEjectionTime: 30s     # 摘除时长
```

被摘除实例经过一段时间后自动重新试探，恢复后重新接入。

## 故障注入：主动制造不可用

要验证韧性策略是不是真有用，可以故意注入延迟和错误，看在有故障时系统表现：

```yaml
spec:
  hosts:
    - reviews
  http:
    - fault:
        delay:
          percentage: { value: 50 }
          fixedDelay: 5s        # 50% 请求注入 5 秒延迟
      route:
        - destination: { host: reviews, subset: v1 }
```

常用于混沌实验：注入 5 秒延迟，看超时和重试是不是按预期触发。能主动测韧性，是网格一个很实用的能力。

## 韧性能力一览

| 能力 | 作用 | 配在哪 |
|---|---|---|
| 超时 | 防慢调用占资源 | VirtualService 路由 |
| 重试 | 补偿瞬时失败 | VirtualService 路由 |
| 熔断 | 摘除坏实例防雪崩 | DestinationRule |
| 故障注入 | 主动验证韧性 | VirtualService 路由 |

## 常见坑

1. 重试非幂等接口：副作用翻倍，只对幂等操作开。
2. 超时不配：慢调用一路堆上去，上游被拖垮。
3. 熔断参数拍脑袋：连续次数、窗口要贴合实际故障形态。

## 小结

超时设上限、重试补瞬时、熔断摘坏实例、注入来验证。四件套都是声明配置，业务零侵入。配好这些，微服务链条才扛得住真实世界的故障。
