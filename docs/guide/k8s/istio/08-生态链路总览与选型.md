# 生态链路总览与选型思考

从容器到编排，从监控到服务网格，这一篇把整个链路串起来，帮你在实际项目里想清楚每层该不该上、上到什么程度。适合作为本章的收尾和总结。

## 四层生态的关系

回头看，这四块各解决不同层次的问题，层层递进：

| 层 | 解决的问题 | 代表 |
|---|---|---|
| 容器 | 单个应用的打包和隔离 | Docker |
| 编排 | 多台机器上容器的调度和自愈 | Kubernetes |
| 监控 | 运行起来之后怎么知道好不好 | Prometheus + Grafana |
| 服务网格 | 微服务之间的流量治理、安全、可观测 | Istio |

## 一条请求的完整旅程

一个用户请求打进来，经过这群基础设施：

```
外部请求 → Istio 网关 → Envoy sidecar → 服务 A
  ├─ 服务 B（旁路 Call）→ Envoy(受管)
  └─ 全程被 Prometheus 采集、被追踪
节点上的 CPU/内存 由 node_exporter 上报
出了问题 → Prometheus 规则触发 → Alertmanager → 通知人
```

## 每层的核心心智模型

- Docker：把软件打成一次构建到处运行的单文件包。
- Kubernetes：声明期望，控制器收敛现实，坏一个补一个。
- Prometheus：拉取指标入库，PromQL 查询，规则告警。
- Istio：sidecar 接管流量，治理横切能力零侵入。

## 该不该上的判断

不是每层都无脑推。规模小、业务简单时，直接 Docker Compose 可能比上 K8s 更省事；服务就几个、治理需求不高时，Istio 的复杂度可能大于收益。

| 场景 | 建议 |
|---|---|
| 单机几个容器 | Docker Compose 足够 |
| 多机、要自愈发布 | 上 Kubernetes |
| 服务多、要统管告警看板 | Prometheus + Grafana |
| 服务众多、治理集中、有平台团队 | 上 Istio |

## 走上这套栈的实际路径

建议循序渐进，不要一次全上：

1. 先用 Docker 把一个应用玩熟：镜像、网络、卷。
2. 上 Kubernetes 托管无状态服务，感受自愈和发布。
3. 接 Prometheus 和 Grafana，把健康看清楚。
4. 服务多起来后再评估 Istio，先灰度再切 STRICT。

## 小结

这一套从容器到服务网格的链路，构成了云原生应用的基础设施。每层的核心都是一种简化：容器简化打包、K8s 简化运维、监控简化判断、网格简化治理。按规模渐进式引入，既能拿到收益，又不被复杂度拖垮。
