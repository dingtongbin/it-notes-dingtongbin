# 可观测性：指标、追踪与访问日志

前面监控篇讲的是独立 Prometheus 采集，Istio 让可观测数据天然齐全：每个服务进出的指标、每个请求的链路追踪、访问日志都由 sidecar 顺手收集。这一篇讲网格能自动提供什么可观测能力。

## 网格带来了什么

由于所有流量都经过 sidecar，网格能自动产出一整套可观测数据，无需业务埋点：

| 数据 | 说明 |
|---|---|
| 指标 | 每个服务的请求量、时延、错误（RED 指标） |
| 追踪 | 每个请求跨服务跳转的完整链路 |
| 访问日志 | 每个请求的元数据（源、目的、状态码、耗时） |

## 服务级指标：RED

Istio 自动产生服务层面的指标，最常见的几个：

- 请求量：每秒多少请求。
- 时延：请求耗时分布。
- 错误：错误率。

这些指标接进 Prometheus 就能查。比如看 P99 时延、某个服务的错误率，一页齐了。业务团队不用自己埋指标，只要调用发生在网格内就有数。

## 链路追踪：一条请求走哪了

当一个请求跨多个服务，追踪把它串成一条链路，能看出每一步耗时在不同服务。配合 Jaeger 这类工具展示：

```
请求 A → auth(10ms) → api(20ms) → db(5ms)
总耗时 35ms，加粗的是慢的那一环
```

定位"一个接口慢了"，从追踪链路里看哪一跳最慢就清楚了。Istio 会自动注入追踪上下文，业务无侵入。

## 访问日志：每个人请求的明细

sidecar 还可以输出每个请求的访问日志，包含：

- 来源地址、目标服务
- 请求路径、方法
- 状态码、耗时、流量标签

这对排查"到底有没有流量、权限哪来的"很有帮助。

## 和 Prometheus/Grafana 的对接

通常配成：

```
Istio 指标 → Prometheus 存储 → Grafana 大盘
Istio 追踪 → Jaeger / Zipkin 展示
访问日志 → 日志系统汇总
```

也就是把前面监控篇的整套接进来，网格负责生产数据，监控体系负责存储展示。很多 Istio 安装自带 addon，把这几套直接铺好。

## 常见坑

1. 指标出不来：确认 sidecar 注入成功、Prometheus 抓取配置对。
2. 追踪串联不起来：需要正确的上下文透传，配置或语言要注意。
3. 访问日志没开：它要显式启用和配置输出位置。

## 小结

Istio 的可观测性是"免费赠送"的：sidecar 自动产出指标、追踪、访问日志，业务代码不写一行埋点。接上 Prometheus 和追踪系统，微服务的体检报告就自动生成了。这和服务网格、监控、服务治理一起，构成了微服务基础设施的重要一部分。
