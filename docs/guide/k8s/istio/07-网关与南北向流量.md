# 网关与南北向流量

前面 VirtualService 治理的流量是服务和服务之间（东西向）。从外部进来的流量（南北向）由网关承接。Istio 的网关用独立部署的 Envoy 作为流量入口，把外部请求按规则路由进网格。这一篇讲 Ingress 下的 Istio 网关。

## 为什么不是直接用 Ingress

K8s 的 Ingress 只覆盖 HTTP 层，且路由能力有限。Istio 网关用专门的 Envoy 实例做入口，能复用服务网格的所有能力：四/七层、路由、重试、熔断、mTLS 出口统一。对网格内服务，内外流量能统一治理。

## 网关的两个部分

Istio 网关由两个资源协作：

| 资源 | 作用 |
|---|---|
| Gateway | 声明入口要监听哪些端口、用哪个证书 |
| VirtualService | 声明这个入口进来的请求怎么路由 |

Gateway 开门，VirtualService 指路。注意这个 VirtualService 也是前面那个 CRD，区别在于它的 gateways 字段指向了网关。

## 定义一个 Gateway

```yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: demo-gateway
spec:
  selector:
    istio: ingressgateway    # 用哪个 Envoy 实例承载
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      hosts:
        - "example.com"
```

它声明了一个 HTTPS 入口，只接收 example.com 的流量。

## 把入口流量路由进服务

再配 VirtualService 把进来的请求转到集群内服务：

```yaml
spec:
  gateways:
    - demo-gateway
  hosts:
    - example.com
  http:
    - match:
        - uri: { prefix: /api }
      route:
        - destination: { host: api.default.svc.cluster.local }
```

这条表明 example.com/api 进来的请求转给集群里的 api 服务，并完整进入网格。之后重试熔断安全这些能力对它同样生效。

## 证书与 TLS 终止

网关通常负责 TLS 终止（和 Ingress 的理解类似），证书配置在 Gateway 的 servers 里，或配合 cert-manager 自动签发。南北向加密在入口完成，网格内继续 mTLS。

## 常见坑

1. Gateway 和 VirtualService 一对多没配好：定义了口但路由没接到。
2. hosts 不匹配：入口收了流量路由不到对应的 VirtualService。
3. 只配 Gateway 忘装/连 ingressgateway：selector 指向的实例要存在。

## 小结

南北向流量 = Gateway（声明入口）+ VirtualService（指明路由）。真正承载的入口 Envoy 常由集群部署。理解了 Gateway 和 VirtualService 的分工，也就理解了整个网格里流量流转的最后一环。
