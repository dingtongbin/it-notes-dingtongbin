# 服务网格与 Istio 是什么

前面集群里微服务靠 Service 彼此发现调用，但很多通用能力——灰度、超时、重试、熔断、限流、双向 TLS——如果每写一个服务都要在代码里实现一遍，开发会疯。服务网格把这套东西从应用代码里抽出来，用基础设施代为处理。这一篇讲服务网格的出现，以及 Istio 的角色。

## 微服务时代的新问题

服务一旦拆成几十上百个模块，麻烦就不再是"能不能调通"，而是这些"通用横切能力"：

- 流量控制：灰度发布、按版本分流。
- 韧性：超时、重试、熔断、限流。
- 安全：服务间双向 TLS、鉴权。
- 可观测：每个调用链路的指标、追踪。

每个服务各写一遍，代码里充满重复的样板逻辑，还难统一。

## sidecar：把能力装进边车

服务网格的答案是不改业务代码，在每个服务旁边塞一个代理（sidecar）。所有进出服务的流量都被这个代理接管，治理逻辑放在代理里。

```
服务 A  ──〓──▶  sidecar  ────〓────▶  sidecar  ──〓──▶ 服务 B
        （业务不用管）        （代理负责治理）
```

对业务代码来说，它只是普通地监听端口、普通地调用下一个服务，治理全被代理透明地做了，代码零侵入。

## Istio 的两大阵营

Istio 由数据面和控制面组成：

- 数据面：跑在每个服务旁边的 Envoy 代理，真正处理流量、采集指标。
- 控制面：istiod 集中管理，把用户的规则翻译成发给各代理的配置。

```
                 ┌─────────────────────────┐
                 │  控制面 istiod            │
                 │  规则 → 下发配置给各代理  │
                 └────────┬────────────────┘
                          │
     服务A──Envoy ── Envoy──服务B
     服务C──Envoy ── Envoy──服务D
```

## 不侵入业务的好处

最大的价值是解耦：流量治理、安全、可观测这些能力，业务团队不用写、不用懂，由平台统一提供。新增灰度、改策略，只改配置文件，不动业务服务。

## 它和 Prometheus 的关系

fit 服务网格天然能产生大量可观测数据：每个代理能上报指标、访问日志和追踪。Istio 通常对接 Prometheus 存指标、Grafana 展示、接入现有追踪系统。前面监控篇讲的东西，到这里正好被服务网格喂数据。

## 什么时候适合上服务网格

网格不是银弹，它带来复杂度（多一个代理、多一份运维）。适合：服务很多、治理需求集中、有专门平台团队。如果服务少治理简单，可能不值得上。

## 小结

服务网格用 sidecar 把横切能力从代码里抽到基础设施。Istio = 数据面（Envoy 处理流量）+ 控制面（istiod 管配置）。理解它"零侵入地给微服务加分发、韧性、安全、可观测"，就抓住了本质。
