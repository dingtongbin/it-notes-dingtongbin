# 监控体系与 Prometheus 是什么

集群跑起来之后，怎么知道它健不健康、哪里在变慢？这就进入监控。Prometheus 是云原生监控的事实标准，通常和 Grafana 一起用。这一篇先建立监控的整体框架，再看 Prometheus 在整个体系里扮演什么角色。

## 监控在回答什么问题

监控的本质是持续回答三个问题：现在快不快（性能）、现在挂没挂（可用性）、为什么（关联定位）。为此需要三类数据，分别解决不同问题：

- 指标：数值型的时间序列，CPU、QPS、请求时延，用于判健康、做告警。
- 日志：记录具体事件和上下文，用于事后分析原因。
- 追踪：一条请求跨多个服务的完整链路，用于定位慢在哪一环。

Prometheus 做的是"指标"这一条线，和日志、追踪配合，才构成完整的可观测性。这一篇主讲指标。

## 为什么选指标

指标是全量的数值，占用小、便于量化、适合做自动化告警和趋势。它们回答了"是否异常"，一旦异常再结合日志和追踪去定位"为什么"。

## Prometheus 在体系里的角色

典型的监控拓扑：

```
应用/节点/中间件（暴露指标）
        │ scrape 拉取
        ▼
    Prometheus（采集 + 存储 + 计算 + 告警规则）
        │
        ├──▶ 存储时间序列数据
        ├──▶ PromQL 查询 / 规则告警
        └───▶ Alertmanager（通知 邮件/webhook）
                 │
                 ▼
            团队 / 值班
```

Prometheus 主动从目标拉取指标，存储，按规则发现异常时触发告警，Alertmanager 负责把告警送到人那里。人们用 API 或工具查询数据画图。

## Prometheus 的拉取模型

不是等目标把数据送上来，而是 Prometheus 主动去每一个目标抓一次。目标通常暴露一个 /metrics 接口，Prometheus 定时来抓。好处是采集节奏统一、目标挂在哪个采集器健康一目了然。

## 一条完整的监控链条

```
暴露指标 → 采集入库 → 查询/可视化 → 规则告警 → 通知
```

从让应用暴露指标开始，到数据进 Prometheus，再到查询出图、配告警规则、最后通知到人，这每一环在后面几篇都会展开。
