# 服务发现

前面的采集配置里目标都是写死的 static_configs。云原生环境里 Pod 会走走停停、扩缩容频繁，手写目标完全不现实。Prometheus 用服务发现自动找到该抓的目标。这一篇讲常见发现机制，重点在 K8s 里的发现。

## 为什么需要服务发现

裸静态配置在 Kubernetes 里行不通：Pod 每秒钟都在变，新的起来旧的走，IP 也不固定。服务发现让 Prometheus 从集群 API 实时拿到资源配置，自动生成抓取目标。

## 几种服务发现

Prometheus 内置多种服务发现器：

| 发现器 | 目标来源 |
|---|---|
| static_configs | 手写死目标（小规模/开发） |
| file_sd | 从一个文件列表读，适合配合外部配置中心 |
| dns_sd | 用 DNS SRV 记录发现 |
| kubernetes_sd | 从 Kubernetes API 发现节点/Pod/Service 等 |
| ec2_sd / gce_sd | 从云厂商发现机器 |

## 在 Kubernetes 里发现 Pod

配置 kubernetes_sd，配合 relabeling 从资源元数据里提取标签，再设定抓取规则：

```yaml
scrape_configs:
  - job_name: kubernetes-pods
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: "true"
```

relabeling 是服务发现的灵魂：它决定哪些目标保留、标签怎么改。上面例子只保留标注了 scrape=true 的 Pod。

## 用注解打标

在 K8s 里，常用注解告诉 Prometheus 该怎么抓某个 Pod：

```yaml
metadata:
  annotations:
    prometheus.io/scrape: "true"
    prometheus.io/path: /metrics
    prometheus.io/port: "8080"
```

服务发现读到这些注解，配合 relabel 把它变成抓取配置，这样开发者只要在自己的 Pod 上加注解，监控就自动接入。

## relabeling 做了什么

relabel 阶段在做两件事：过滤目标（keep/drop），以及把元标签改写或保留成最终标签。理解 relabel 就理解了服务发现在实际配置里怎么落地。容器内抓取、只抓有监听的目标，都靠它。

## 不是所有对象都得发现

| role | 发现的资源 |
|---|---|
| pod | Pod 本身 |
| service | Service 后的 Pod |
| node | 节点（配合 node_exporter） |

按你的监控对象选 role；不一定都要自己配，云端很多现成方案也会帮你配置好发现。

## 常见坑

1. 注解没写或写错，目标一直抓不到。
2. relabel 正则写不对，目标被过滤掉。
3. 发现的目标太细或太多，把序列数量顶爆。
4. 自建静态配死 IP 在云原生里很快失效。

## 小结

服务发现把"找该抓什么"从人工写死变成自动从集群现状提取。配合 relabel 和注解，应用接入监控就能做到"加了注解就自动被抓"，这是云原生监控能落地的前提。
