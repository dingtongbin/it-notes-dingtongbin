# 节点维护与集群排障

集群不只是写 YAML。日常还要对付节点维护、故障排查。这一篇讲怎么把节点安全地下线维护（cordon/drain）、节点管理命令，以及一套排障思路。

## 三个维护命令

| 命令 | 作用 |
|---|---|
| kubectl cordon node01 | 标记节点"暂不调度新 Pod"，已有 Pod 不动 |
| kubectl drain node01 | 把节点上的 Pod 赶走并清位，安全下线 |
| kubectl uncordon node01 | 恢复调度，可以再放新 Pod |

drain 不是强杀：有强制删除保护的先优雅驱逐，确保 Pod 能在别的节点重建。维护流程通常是 cordon → drain → 修机器 → uncordon。有 DaemonSet 之类的系统组件需要 --ignore-daemonsets 才能 drain。

## 排查常用命令

```bash
kubectl get nodes                     # 节点状态
kubectl describe node node01          # 看节点资源、污点、事件
kubectl get pods -A                   # 所有命名空间看 Pod
kubectl top nodes                     # 节点资源实时占用
kubectl top pods                      # Pod 资源占用
```

## 一套排障思路

按"从大到小"收敛：

1. 先看集群整体：节点不是 Ready，那就不是应用问题。
2. 再看工作负载：Deployment 是不是一直没就绪。
3. 看单个 Pod：describe 里的事件往往直接给原因。
4. 进容器看：exec 进去看进程、日志、网络。

## 常见症状与原因

| 症状 | 常见原因 |
|---|---|
| Pod 一直 Pending | 没节点满足调度（资源/污点/选择器） |
| Pod CrashLoopBackOff | 启动就崩，探针或命令有问题，看 logs |
| ImagePullBackOff | 镜像拉不到或拉私有失败 |
| 节点 NotReady | 网络、kubelet、资源耗尽 |
| 服务访问不通 | endpoints 空、网络策略、探针摘除 |

## 排障的关键顺序

```
get → describe → logs → 确认现状
先看状态，再用 describe 找原因，最后 logs 看日志
```

别一开始就钻进容器，先让 kubectl 告诉你大概哪一环。

## 思考：自愈之后人该管什么

K8s 自愈了容器层的故障，但硬件、配置、容量这些还要人盯。节点挂了 K8s 会把上面的 Pod 迁去别的节点重建，但如果是配错了全局配置、打错了污点，K8s 不知道，得靠人的排查能力兜底。排障能力由此变得比记忆命令更重要。

## 小结

节点维护靠 cordon/drain/uncordon 三步，排障靠 get/describe/logs 递进。核心不是背命令，而是建立"从集群到单容器逐层收敛"的排查思路。
