# 命名空间、标签与选择器

集群里资源多到一定程度，需要做两层组织：物理上按命名空间分隔，逻辑上用标签选择。这一篇讲命名空间怎么隔离，以及标签和选择器怎么把资源分组挑选。

## 命名空间：虚拟隔离

命名空间把一个集群从逻辑上切成多个小集群：

```bash
kubectl create namespace test
kubectl get pods -n test
```

作用：同名资源在不同命名空间互不冲突；配合配额限制 namespace 的资源用量；用 RBAC 给不同团队划分权限。看 Pod 时若不指定 -n，默认看 default 命名空间。

跨命名空间访问要带全名（web.default.svc），本命名空间直接用短名，这在前面的 Service 篇讲过。

## 标签：给资源做标记

标签是附在资源上的一对键值，用来组织和挑选：

```yaml
metadata:
  labels:
    app: web
    env: prod
    tier: frontend
```

标签不参与功能，只用于挑选。可以随便加、改，不像名字那样限制多。

## 选择器：按标签挑资源

用命令查看时用 -l：

```bash
kubectl get pods -l app=web
kubectl get pods -l 'env=prod,tier=frontend'
```

而工作负载内部用 matchLabels 声明它该管哪些 Pod：

```yaml
selector:
  matchLabels:
    app: web
```

Service、Deployment 都靠这套标签选 Pod。合理设计标签维度，能让运维和排错高效很多。

## 常用的标签维度

- 环境：env=dev/prod
- 应用：app=web
- 分层：tier=frontend/backend/data
- 版本、负责人等按团队习惯

## 常见坑

1. 忘带 -n 看错对象：跨命名空间要明确指定。
2. selector 写错匹配不到：Pod 一直挂着但没人管，describe 很容易看漏。
3. 命名空间开太多：配额、RBAC 都要配，管理和开销随之上升。
4. 标签改乱：改标签会影响依赖它的选择器，改前想清楚。

## 小结

命名空间管"分离"，标签管"挑选"。一个资源通常既是某命名空间的一员，也带着若干标签被各类选择器关联起来。这两套机制是 K8s 组织资源的基础。
