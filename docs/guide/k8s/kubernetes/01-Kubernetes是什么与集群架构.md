# Kubernetes 是什么与集群架构

Docker 解决了单机跑容器，但一到多台机器、几百上千个容器，问题就多了：跨机器部署、故障自愈、服务发现、滚动发布、扩展收缩。Kubernetes 就是把这些编排能力做成一个集群系统。这一篇先建立整体认知：它解决了什么问题、集群里有哪些角色。

## 它解决什么

单机 Docker 的短板：一台机器挂了容器不一定自动换台机器；多台机器间的调度没有统一入口；容器 IP 会变，服务发现要自己折腾；滚动发布、自动扩缩容都要手写。K8s 把这些问题变成声明式的：你描述"要几个副本、什么镜像"，它负责把现实调整成你描的样。

## 声明式的核心思想

你写 YAML 声明期望状态，比如"3 个 nginx 副本"。控制器负责收敛：现在的数量是 3，就一直维持；有容器挂了，自动起新的补上。你不需要告诉它"第 2 个挂了，去重启第 2 个"，只要声明目标，它自己比对并修补。

## 集群的角色分工

一个 K8s 集群分两大阵营：控制平面和节点。

```
┌────────────── 控制平面 Control Plane ──────────────┐
│  API Server   所有操作用户入口，一切命令的入口       │
│  etcd         集群状态存储，K8s 的数据库             │
│  Scheduler    决定新 Pod 调度到哪个节点              │
│  Controller   各种控制器，把现状收敛到期望状态       │
└──────┬────────────────────────────────────────────┘
       │ 下发调度、状态汇总（kubelet 汇报）
       ▼
┌────────────── Worker 节点 ─────────────────────────┐
│  kubelet      每个节点上的执行者，管本节点 Pod      │
│  kube-proxy   实现服务发现和负载均衡的流量规则       │
│  容器运行时    Pod 里的容器真正跑在这个上面          │
└────────────────────────────────────────────────────┘
```

## 控制平面：大脑

- API Server：所有组件和 kubectl 都通过它交互，是集群唯一的入口，它负责鉴权、校验、转发。
- etcd：一个分布式键值库，存集群所有状态。读到的集群样子，就来自这里。
- Scheduler：新建 Pod 时，它根据资源、约束挑一个合适的节点。
- Controller Manager：一批控制器（Deployment 控制器、节点控制器…）各自盯着自己负责的一类资源，发现偏差就修补。

## 节点：手脚

- kubelet：每个节点上的代理，负责启停本节点的容器，并持续向控制平面汇报健康，是控制面触达具体负载的执行者。
- kube-proxy：把 Service 的虚拟 IP 转成到具体 Pod 的转发规则，实现负载均衡。
- 容器运行时：比如 containerd，负责真正拉起容器。

## 一句话理解

控制平面想起目标，节点负责干活，kubelet 是把两头连起来的信使。所有对集群的操作都走 API Server，所有状态都存在 etcd，整个系统围绕"期望状态 vs 实际状态"自我修复。
