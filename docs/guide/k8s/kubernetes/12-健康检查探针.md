# 健康检查探针

K8s 要判断容器到底是"活着"还是"准备好了"。探针就是让 K8s 知道容器状态的手段，分存活、就绪、启动三种，各自决定不同的行为。这一篇讲三类探针和常见的探测方式。

## 三类探针

| 探针 | 作用 | 失败后果 |
|---|---|---|
| livenessProbe 存活 | 容器还活着吗 | 失败就重启容器 |
| readinessProbe 就绪 | 能不能接收流量 | 失败就从 Service 摘掉，不转发流量 |
| startupProbe 启动 | 启动慢的应用什么时候算起好了 | 启动期间不查其余探针 |

核心区别：liveness 管"要不要重启"，readiness 管"要不要接流量"。

## 配置一个 HTTP 探针

```yaml
spec:
  containers:
    - name: api
      image: myapp:v1
      readinessProbe:
        httpGet:
          path: /healthz
          port: 8080
        initialDelaySeconds: 3
        periodSeconds: 5
      livenessProbe:
        httpGet:
          path: /healthz
          port: 8080
      ports:
        - containerPort: 8080
```

## 探测的三种方式

| 探测方式 | 说明 |
|---|---|
| httpGet | 请求一个 HTTP 地址，返回 2xx/3xx 就算成功 |
| tcpSocket | TCP 端口能连上就算成功 |
| exec | 容器里跑一条命令，退出码 0 算成功 |

httpGet 最常用，适合有 HTTP 服务的容器；tcpSocket 适合没 HTTP 只有端口的；exec 适合一般进程。

## 参数怎么调

- initialDelaySeconds：容器启动后多久才开始探测，给应用一点启动时间。
- periodSeconds：多久探测一次。
- timeoutSeconds：单次探测超时。
- failureThreshold：连续失败多少次才判为失败。

启动慢的应用要适当调大 initialDelaySeconds 或加 startupProbe，避免刚刚起来就被 liveness 判死重启。

## readiness 和 liveness 的分工

典型设计：readiness 用健康接口判断能否接流量，liveness 用同一个接口或更严的检查判断该不该重启。接口里可以区分"只是依赖还没就绪"和"真的坏了"——前者返回非 2xx 让 readness 摘掉但不至于重启，后者触发 liveness 重启。

## 常见坑

1. 只配 liveness 不配 readiness：依赖还没好就被强杀或反复重启。
2. 探针参数太紧：启动慢的应用一直被打死，陷入重启循环。
3. 探针端到不对外服务的端口：路径、端口配错，一直判失败。
4. 把对外健康接口当 liveness 用时依赖外部：探测依赖了就不稳定。

## 小结

探针把"容器是死是活"从主观判断变成客观检查。配好探针，滚动更新、自动重启、流量摘除才能真正正确工作。这是生产稳定性的基础之一。
