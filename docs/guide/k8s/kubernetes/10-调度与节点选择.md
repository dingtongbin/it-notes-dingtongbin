# 调度：节点选择、亲和性与污点

调度器决定 Pod 放哪台节点，但有些 Pod 必须/一定要避开某些节点。这一篇讲怎么控制调度：节点选择器、亲和性、以及用污点容忍来实现"某些节点只给某些负载用"的隔离。

## nodeSelector：按标签挑节点

给节点打上标签，然后用 nodeSelector 让 Pod 必须去带这个标签的节点：

```bash
kubectl label node node01 disktype=ssd
```

```yaml
spec:
  nodeSelector:
    disktype: ssd       # 只调度到打了这个标签的节点
```

这是最朴素的调度约束：标签要求满足才放。

## 节点亲和性（亲和/反亲和）

nodeSelector 只有"必须满足"，亲和性更精细：分成需要硬性满足的 requiredDuringScheduling 和尽量满足的 preferredDuringScheduling。

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: zone
                operator: In
                values: ["zone-a"]
```

亲和性除了节点层面的 nodeAffinity，还有 Pod 层面的 podAffinity/podAntiAffinity，可以让某些 Pod 尽量聚在同一节点，或者绝对不许在同一节点（比如两副本别放一台机器）。

## 污点与容忍：反向的控制

标签亲和是"我想去哪"，污点是"我这里你别来"。给节点打污点后，没有对应容忍的 Pod 不会被调度到这里。

```bash
kubectl taint nodes node01 key=value:NoSchedule
```

普通的 Pod 默认不会去带污点的节点。只有声明了对应容忍的 Pod 才被允许：

```yaml
spec:
  tolerations:
    - key: "key"
      operator: "Equal"
      value: "value"
      effect: "NoSchedule"
```

污点有三种效果，按它们对已有 Pod 的态度区分：NoSchedule 不再调度新的来、NoExecute 已有的也可能被赶走。

## 典型场景

| 需求 | 手段 |
|---|---|
| GPU 任务去有 GPU 的机器 | 节点标签 + nodeSelector/亲和 |
| 数据库副本别放同一节点 | podAntiAffinity 打散 |
| 专机跑某类高优任务，别的别来 | 节点污点 + 专属容忍 |
| 维护某台节点先别调度新 Pod | 给节点加 NoSchedule 污点 |

## 常见坑

1. nodeSelector 没节点满足：Pod 一直 Pending，查节点标签。
2. 污点挡住所有 Pod 也想看：给负载加对应容忍。
3. 理解错 required 与 preferred：前者调度不进就卡，后者只是尽量。
4. 直接在节点上乱打污点：影响面大，先看清楚 effect。

## 小结

调度控制分正向和反向两条线：正向用标签 + 亲和性给 Pod 找合适的地方，反向用污点 + 容忍防止不合适负载入侵。两条都掌握，调度就完全在你手里了。
