# 资源请求与限制 Requests/Limits

容器需要多少资源、最多能用多少，K8s 用资源的 requests 和 limits 声明。这是调度和资源保护的关键：调度器靠 requests 选节点，kubelet 靠 limits 防止某个容器吃光机器。这一篇讲这两个字段的区别和用法。

## requests 和 limits

| 字段 | 语义 | 用途 |
|---|---|---|
| requests | 保证，调度依据 | 调度器保证节点能腾出这么多给这个 Pod |
| limits | 上限，资源保护 | 容器最多用这么多，超了限制或被杀 |

核心思想：requests 是"我需要这么多"，limits 是"我最多用这么多"。

```yaml
spec:
  containers:
    - name: api
      image: myapp:v1
      resources:
        requests:
          cpu: "500m"        # 0.5 个 CPU
          memory: "512Mi"
        limits:
          cpu: "1"           # 最多 1 个 CPU
          memory: "1Gi"
```

## CPU 的单位

CPU 单位 1 表示一个 CPU 核，500m 表示半个核。m 是毫核，1000m = 1 核。CPU 是压缩资源：超了 limits 只是被限速，不会被杀，因为可以排队。

## 内存的单位

内存用 Mi、Gi 等单位，Gi 是 2 的 30 次方字节，1024Mi = 1Gi。内存是非压缩资源：超了没地方放，导致 OOM，容器可能被杀。所以内存必须设 limits，这是重要的保护。

## requests 怎么帮调度

调度器为新 Pod 找节点时，会累加节点上所有已调度 Pod 的 requests，剩下的空闲必须装得下新 Pod 的 requests，否则不选这个节点。所以 requests 是调度器决定"放哪"的依据，设得过大浪费资源、过小则可能挤爆。

## limits 怎么保护节点

kubelet 保证容器实际占用不超过 limits。内存超 limits 直接 OOM 杀掉容器；CPU 超 limits 则限速。limits 是集群不被单一失控容器拖垮的防线。

## CPU 和内存的区别

| 特性 | CPU | 内存 |
|---|---|---|
| 压缩资源 | 是，超了限速 | 否，超了 OOM |
| 超 limits 后果 | 变慢 | 被杀 |
| 是否建议设 limits | 建议 | 必须 |

## 关于何时设置

生产通常要求：每个容器都设 requests 和 limits。不设 requests 的 Pod 可能被调度到已很挤的节点，影响稳定性；不设 limits 的内存容器可能 OOM 整个节点。基于真实负载数据设置，别拍脑袋。

## 常见坑

1. 只设 limits 不设 requests：调度时按 0 计算，可能超售。
2. 内存超 limits 被杀还不解：看 OOMKilled 状态，调大 limits 或减并发。
3. 全部容器都用默认值：给每个容器明确声明是更稳妥的做法。
4. requests 远大于实际需求：浪费，调度率低。

## 小结

requests 是调度承诺、limits 是资源红线，两者一起决定了 Pod 用得稳定又不伤邻居。设值时用真实压测数据，而不是随便填，才能既省又稳。
