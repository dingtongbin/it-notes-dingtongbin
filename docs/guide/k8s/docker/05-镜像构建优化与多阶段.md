# 镜像构建优化与多阶段构建

Dockerfile 谁都会写，但写出又小又快又是另一回事。这一篇讲两个核心优化手段：利用构建缓存、用多阶段构建砍掉运行时不需要的东西。这两招能让镜像体积从几百 MB 缩到几十 MB。

## 优化一：利用构建缓存

构建每次都是从上下文开始逐条执行指令。Docker 会对每条指令算一个缓存键，如果这条指令和它前面的都没变，就复用缓存层，跳过执行。

要利用这个特性，就得把指令按"变的频繁程度"从低到高排列：

```dockerfile
FROM node:20
WORKDIR /app
COPY package.json package-lock.json ./   # 依赖清单
RUN npm ci                               # 装依赖（除非依赖变了，否则恒缓存）
COPY . .                                 # 源码（经常变，放最后）
CMD ["npm", "start"]
```

如果先 COPY 源码再 RUN npm install，那么每改一行源码，整个依赖安装都要重来。

## 优化二：多阶段构建

运行一个应用往往需要编译工具链，但运行时只需要编译好的产物和运行环境。多阶段构建用多个 FROM，先把编译装好的一堆依赖留在中间阶段，最后只把产物拷进一个干净的基础镜像：

```dockerfile
# 阶段一：编译（用完整工具链）
FROM golang:1.22 AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o server .

# 阶段二：运行（用最精简的基础镜像）
FROM scratch
COPY --from=builder /src/server /server
ENTRYPOINT ["/server"]
```

scratch 是空镜像，没有任何系统层，运行时就一个二进制，体积最小。产物从几百 MB 缩到几十 MB 甚至几 MB。

## 多阶段的其他受益

- 构建环境的工具链、源码、中间文件都不进最终镜像，更安全。
- 每个阶段可以单独选基础镜像，构建阶段用方便的工具，运行阶段用精简的。
- 多阶段不增加最终镜像的层，中间阶段只是构建过程的一部分。

## 常用精简基础镜像

| 基础镜像 | 特点 |
|---|---|
| scratch | 空，只能跑静态二进制（如纯 Go 无 CGO） |
| alpine | 极小的 Linux，几 MB，含 musl 和包管理器 |
| distroless | Google 提供，无 shell、无包管理器，只够跑应用 |

选精简镜像能显著减小体积，但要注意：如果依赖动态链接库或需要 shell 调试，可能要放弃部分精简。

## 小结

优化的两条主线：让缓存最大命中和让最终镜像最小。顺序固定"不变的在前"，产物单独一层搬过去，配合精简基础镜像，就能得到又小又快的构建。
