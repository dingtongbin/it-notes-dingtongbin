# 数据卷与挂载

容器的文件系统是可写的，但容器一删，里面的数据就没了。为了让数据活过容器生命周期，或者让宿主和容器共享文件，需要卷。这一篇讲三种持久化方式。

## 为什么容器里的数据会丢

容器最上层是可写层，但容器本身是临时的事故现场：docker rm 一删，整个文件系统就没了。数据库、上传文件、日志这些要持久的数据，必须放到容器之外。

## 三种挂载方式

| 方式 | 数据在哪 | 谁管理 | 适用 |
|---|---|---|---|
| volume | 宿主 /var/lib/docker/volumes | Docker 管理 | 生产持久化，推荐 |
| bind mount | 宿主任意路径 | 你自己管理 | 开发共享源码、传配置 |
| tmpfs | 宿主内存 | Docker | 临时、内存级数据，不想落盘 |

### Volume

```bash
docker volume create data
docker run -d -v data:/var/lib/mysql mysql
```

左边是卷名，右边是容器内路径。数据存在 Docker 管理的目录里，备份、迁移都有统一入口。

### bind mount

```bash
docker run -d -v /host/path:/app/config app
```

把宿主任意目录映射进容器。开发时常把自己的源码目录挂进去，改代码即时生效，避免反复重新构建镜像。

### tmpfs

```bash
docker run -d --tmpfs /tmp app
```

数据只在内存里，容器停止即消失，适合缓存、临时文件。

## 通过 -v 还是通过持久化思想

-v 的语法是 宿主或卷名:容器路径[:模式]。掌握之后用 Dockerfile 里 VOLUME 声明的匿名卷，或用 Compose 里的 named volume 更规范。

## 写时先想：这份数据要活多久

一个简单的判断：数据要不要在容器删除后继续存在？要，就用卷或 bind；只是容器运行期间的内存临时数据，用 tmpfs。数据库、用户文件必须卷；临时缓存可以 tmpfs。

## 常见坑

1. bind mount 目录不存在：Docker 会自动创建，但权限和预期可能不符。
2. 卷里文件权限不对：挂载有时会覆盖容器的文件属主，注意用户映射。
3. 忘挂卷：容器一删数据没了才发现，数据库这类必须尽早用卷。
4. 误把整个源码目录 bind 进生产镜像：生产一般用卷或镜像内置，不在运行时挂源码。
