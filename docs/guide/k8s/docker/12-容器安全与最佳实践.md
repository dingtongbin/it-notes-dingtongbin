# 容器安全与最佳实践

容器听起来轻巧，但生产里有一堆安全坑。这一篇讲几类最常见的安全问题和对策，以及一套写 Dockerfile 和跑容器的基线实践。安全不是一次性工作，而是渗透在每一步的习惯。

## 别用 root 跑进程

默认容器里以 root 运行，一旦应用被攻破，攻击者在这个容器里就是 root。解决：

```dockerfile
USER appuser          # 从 root 切换到非特权用户
```

最好在镜像里加一个专用用户然后切过去。实在要给低权限能力，用 capability 白名单而不是干脆给 root。

## 最小化 attack surface

- 镜像越小越好：用精简基础镜像，少装工具，就少一个被利用的入口。
- 尽量不用 latest：latest 不可追溯，用固定版本的镜像。
- 别在镜像里放 secret：环境变量、构建参数都要到运行时注入，不进镜像层。

## 只读文件系统

很多进程根本不需要写文件系统。把文件系统设成只读，能防住利用写盘的一些攻击：

```bash
docker run -d --read-only myapp
```

需要写的地方单独挂卷。这样即使被攻破，也写不进去。

## 资源限制就是安全

之前讲的 -m、--cpus 不只是健壮性问题：一个不受限的容器能 CPU 打满、内存吃光，进而影响同宿主其他容器。安全边界的一部分就是资源边界。

## 网络最小化

只暴露必要的端口，多用自定义网络让服务默认互不可达，再按需连通。不要图省事把容器全放 host 网络。

## 镜像来源可信

只从可信仓库拉镜像，扫描镜像里的已知漏洞。企业里常有镜像安全扫描环节，把带高危漏洞的镜像挡在上线前。

## 一套基线实践清单

[ ] 用非 root 用户跑进程
[ ] 选用精简、固定版本的基础镜像
[ ] secret 不进镜像，运行时注入
[ ] 尽量只读文件系统 + 单独卷
[ ] 设置明确的资源限制
[ ] 只暴露必要端口，网络最小化
[ ] 只拉可信仓库镜像并做漏洞扫描

## 小结

Docker 安全的核心是纵深防御：每一层都收敛一点权限，整体风险就小很多。把这些习惯固化成清单，每次构建和部署都过一遍，比事后补救有效得多。
