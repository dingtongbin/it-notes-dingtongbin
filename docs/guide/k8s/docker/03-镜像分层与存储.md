# 镜像分层与联合文件系统

之前提到镜像由一层层组成，这一篇深挖这种分层到底怎么存、怎么运行、为什么这么设计。理解了镜像分层，才能真正看懂 Dockerfile 的每条指令和镜像大小优化。

## 镜像是一个个只读层的堆叠

构建镜像时每一条命令产生一层，这些层都是只读的。运行时在顶层再加一个可写的容器层。

```
镜像层（只读）       容器层（可写）
  layer4  应用       ┌─────────┐
  layer3  依赖     ▸ │ 改动    │  运行时写这里
  layer2  运行环境    └─────────┘
  layer1  基础系统
```

读文件时从上往下找，最顶层优先；写文件时只写进容器层，底下的镜像层永远不变。

## 什么是写时复制

写文件不会真的去改只读的镜像层，而是在容器层复制一份出来再改，这就是写时复制。效果是：任意多个容器共享同一套镜像层，各自启动都很轻；不管下面用了多久，镜像本身不会被污染。

## 分层的目的

- 磁盘复用：几十个基于同一个基础镜像的容器，底层只存一份。
- 传输高效：拉新镜像只传变化的部分，Push 也一样。
- 缓存友好：构建时只有变了的层需要重建，没变的层直接复用缓存。

这也是下一篇讲 Dockerfile 时，为什么指令顺序会影响构建速度的根本原因。

## 提交容器变化为镜像

容器层里的改动可以用 commit 固定成新的镜像层：

```bash
docker commit <容器> myimage:v1
```

平时开发很少直接用 commit（容易产生混乱的层），但它是理解"层"概念的好例子：commit 就是把当前容器层快照成一个新镜像层叠加到原镜像上。

## 查看镜像的分层

```bash
docker history nginx   # 列出镜像每一层的历史
```

会看到一层层以及每层的构建指令。对比不同镜像的 history，能直观看到谁层多、谁层大。

## 小结

镜像分层是整个容器技术的核心之一，后面所有环节——Dockerfile 构建、镜像大小优化、多阶段构建、K8s 的镜像拉取——都建立在这套分层模型之上。
