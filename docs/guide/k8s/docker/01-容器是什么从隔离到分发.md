# 容器是什么：从隔离到分发

Kubernetes 的根基是容器。不把容器讲透，后面的编排都是空中楼阁。这一篇先解决三个问题：容器到底是什么、它和虚拟机差在哪、以及为什么它能让软件"一次构建到处运行"。

## 容器是一种进程隔离

容器不是虚拟机，它本质上就是操作系统里的一个普通进程，只是被额外的机制"关"在了一个独立空间里。这个空间里有自己独立的文件系统、网络、进程树，看起来像一台小机器，实际共享宿主机内核。

实现这种隔离的核心是 Linux 两大机制：namespace 负责"看得到什么"，cgroup 负责"能用多少"。

## namespace：隔离视角

namespace 让一组进程各自看到独立的系统视图。常用的几类：

| namespace | 隔离内容 | 作用 |
|---|---|---|
| PID | 进程编号 | 容器内看到的 1 是自己的主进程，看不到宿主其他进程 |
| Mount | 挂载点 | 容器有自己独立的文件系统树 |
| UTS | 主机名 | 容器有自己的 hostname |
| Network | 网络栈 | 容器有自己的网卡、IP、端口 |
| User | 用户 ID | 容器内 root 不一定映射宿主的 root |
| IPC | 进程间通信 | 独立的消息队列等 |

有了这些隔离，容器里以为自己在独占一台机器。

## cgroup：限制资源

光隔离还不够，还要防止一个容器吃光整台机器。cgroup 限制每个容器能用的 CPU、内存、磁盘 IO、网络带宽。比如一个容器最多用 4 核、2G 内存，超了就受限。这在后面 Docker 的资源限制和 K8s 的 limits 里都是同一套机制。

## 分层的镜像：文件系统是怎么"假装的"

容器的文件系统不是装出来的一整个系统，而是由一层层只读镜像叠加出来，最上面一层是可写的容器层。改文件其实是在最上面的可写层记一个"差异"，不会动到底下的镜像层。

```
┌───────────────────┐  容器层（可写，运行时变化）
├───────────────────┤
│    应用层          │  ─┐
├───────────────────┤   │
│    运行时层        │   │ 各镜像层只读
├───────────────────┤   │
│    基础系统层      │  ─┘
└───────────────────┘
```

这带来两个好处：多个容器共享底层镜像只占一份磁盘；镜像的传输只需传新增的差分层。

## 容器 vs 虚拟机

| 对比点 | 容器 | 虚拟机 |
|---|---|---|
| 内核 | 共享宿主机内核 | 每个有独立内核 |
| 启动 | 毫秒级 | 秒级甚至更慢 |
| 资源 | 只占进程开销，几乎零 | 每个要完整 OS 开销 |
| 隔离 | 靠 namespace/cgroup，偏弱 | 硬件级隔离，更强 |
| 镜像大小 | MB 级 | GB 级 |

写法一换，整个后端基础设施都跟着变了：以前部署是装环境、配系统，现在部署是拿一个镜像跑起来。

## 一次构建，到处运行

把应用、依赖、配置全打进镜像，这个镜像在任何装了 Docker 的机器上跑起来结果都一样。这正是分发和后面 K8s 大规模调度的前提。
