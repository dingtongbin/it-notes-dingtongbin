# 文件系统简介

分区做完了，接下来要往分区里放文件系统，否则它只是一堆没有语义的字节。这篇文档对比 ext4、xfs、btrfs 三大主流文件系统的特性、最强适用场景与各自的坑，帮你在一开始就选对文件系统，避免上线后大规模迁移的麻烦。

## 文件系统是做什么的

文件系统解决的问题是：在原始块设备之上，提供文件、目录、权限、元数据（文件名、大小、时间戳）和一致性保障。内核把对文件系统的调用翻译成对底层设备的块读写，并且用日志（journaling）机制保证异常断电后文件系统不损坏。

Linux 上常见的通用文件系统有 ext 家族（ext4）、XFS、Btrfs 等。这里只讨论生产最常部署的三种。

## 三大家族的定位

| 文件系统 | 出处 | 日志机制 | 强项 | 典型用途 |
| --- | --- | --- | --- | --- |
| ext4 | Linux 内核原生 | 传统日志 | 兼容性好、工具成熟 | 通用数据盘、启动分区 |
| xfs | SGI 开源 | 日志 | 大文件、高并发写入 | 大容量数据盘、数据库 |
| btrfs | Oracle 发起 | 写时复制 | 快照、子卷、校验 | 桌面与实验场景 |

XFS 默认不支持收缩（缩小要退出后重建），ext4 则支持在线 shrink（缩小）。生产上数据库数据目录、大容量文件服务器常用 XFS；通用系统盘、需要随时调整边界的数据通常用 ext4；Btrfs 适合需要合法快照和单个子卷形态管理的场景，但其复杂的内部机制在停机维护时对运维要求更高。

## 三种文件系统的关键差异

逻辑卷的大小动态增长方向差异，直接影响后面扩容。XFS 扩容方便、缩容几乎不可能；ext4 既能扩大也能在满足约束时缩小。这意味着你在选型时就要想清楚"这块盘以后会不会需要缩小"。

日常运维的另一个差异是默认块大小和 inode 数量的设计取向。ext4 默认适合海量中小文件；XFS 用可扩展的 inode 与优化大文件的分配器，对单大文件、持续高吞吐的写入非常友好。Btrfs 通过子卷（subvolume）与写时复制（COW）把快照做成近乎免费的操作，代价是元数据更复杂，占用更多 CPU 与内存。

## 各文件系统的官方工具链

每个文件系统自带一套管理工具，命名都有 mkfs.<fs> 的规律。后续文档会逐一详解，这里先建立一个印象：

| 文件系统 | 格式化命令 | 检查修复命令 | 扩容命令 |
| --- | --- | --- | --- |
| ext4 | mkfs.ext4 | fsck.ext4 | resize2fs |
| xfs | mkfs.xfs | xfs_repair | xfs_growfs |
| btrfs | mkfs.btrfs | btrfs check | btrfs filesystem resize |

工具名称本身就是一个强烈的信号：看到 resize2fs 就知道是 ext4 相关的扩容，看到 xfs_growfs 则是 XFS 专属。

## 怎么看当前文件系统

```bash
lsblk -f
```

```bash
df -T
```

FSTYPE 一列、还有 df -T 的 TYPE 字段都能直接告诉你常用分区的文件系统类型，排查或审计时先看这两处。

生产实践建议：不要为了追求新颖选择没人维护的文件系统。考虑一个文件系统是否成熟，看它的配套工具、热修复补丁频率以及你团队是否有人会维护。长期运行且团队工具链熟，那么通用数据盘选 ext4，大容量高吞吐选 XFS 是低风险选择。

## 小结

选文件系统本质是选扩容模型和一致性代价：ext4 兼容稳健、可扩容可缩容，适合通用盘；xfs 大文件高吞吐、扩展方向友好，适合数据盘和数据库目录；btrfs 快照能力强、结构复杂，适合需要子卷和快照能力的场景。判断文件系统类型用 lsblk -f 与 df -T，后续所有格式化、挂载、扩容文档都会基于这三种文件系统展开。
