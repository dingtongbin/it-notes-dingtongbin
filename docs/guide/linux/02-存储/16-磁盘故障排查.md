# 磁盘故障排查

盘有病，系统会说话：dmesg 里翻异常、SMART 里看体检、smartctl 做预测。这一篇讲接到"盘可能有问题"的信号后，按什么顺序定位与处置。

## 排查总路线

1. 看现象：IO 卡顿、报错、盘消失。
2. dmesg 定位内核报错，锁定设备。
3. SMART 体检确认硬件健康度。
4. 文件系统层面 fsck 修复。
5. 处置：换盘、重建、恢复数据。

## 第一站：dmesg

内核对所有磁盘异常都会留痕，看最近的磁盘相关消息：

```bash
sudo dmesg -T | grep -iE "sata|scsi|ata|I/O error|ext4|xfs" | tail -50
```

重点关注：

- I/O error, dev sdb, sector xxx：读写下坏扇区，盘在硬坏的路上。
- ata... failed command / timeout：命令超时，链路或盘体故障。
- EXT4-fs error / XFS：文件系统逻辑出错，常是底层错误传导上来。
- detached / removed：盘掉线了，检查线缆与背板。

dmesg -T 带人类可读时间戳，方便对齐故障时刻。

## 第二站：SMART 体检

smartmontools 读取硬盘自检数据：

```bash
sudo apt install smartmontools
sudo smartctl -a /dev/sdb
```

重点指标：

| 属性 | 含义 | 危险信号 |
| --- | --- | --- |
| Reallocated_Sector_Ct | 重新分配的扇区数 | 大于 0 且持续增长 |
| Current_Pending_Sector | 等待重映射的扇区 | 大于 0 就要警惕 |
| Offline_Uncorrectable | 无法修复的扇区 | 大于 0 |
| Power_On_Hours | 通电小时数 | 结合寿命参考 |

做一次完整自检（长测试，机械盘约几十分钟到几小时）：

```bash
sudo smartctl -t long /dev/sdb
sudo smartctl -l selftest /dev/sdb
```

SSD 同样支持 SMART，看 Media_Wearout_Indicator（磨损度）与 Percentage Used。

## 第三站：文件系统检查

底层确认有错后，检查文件系统。umount 后执行：

```bash
sudo umount /mnt/data
sudo fsck -f /dev/sdb1          # ext4
sudo xfs_repair /dev/sdb1       # xfs
```

fsck 交互式问"是否修复"，批量自动修复用 -y。xfs 的挂载状态下可先 xfs_repair -n 只查不修。

根分区没法 umount，通常重启进恢复模式或用 LiveCD 再 fsck。

## 处置：坏盘下线

确认盘坏了，从 LVM/RAID 里安全摘除（具体命令见 LVM 与 RAID 两篇）：

```bash
sudo pvmove /dev/sdb            # LVM：先迁走数据
sudo vgreduce datavg /dev/sdb
# RAID：--fail 后 --remove
```

换盘后按原架构重建回池。

## 预防性监控

平时就开着 smartd 自动监控，异常写系统日志：

```bash
sudo systemctl enable --now smartd
```

配置在 /etc/smartd.conf，可加 -m root 让它邮件告警。配合监控篇的 Prometheus node_exporter，磁盘健康指标可以进大盘。

## 常见错误自查

- dmesg 有 I/O error 但 SMART 全绿 → 可能是线缆、背板或控制器问题，换线换口试。
- smartctl 报 Unknown USB bridge → USB 盒装盘读不到 SMART，直连 SATA 再测。
- fsck 越修丢文件越多 → 底层硬件故障未解决先别修文件系统，优先镜像备份（ddrescue）。
- 盘偶尔 timeout 但之后恢复 → 灰色地带，设好监控盯 Reallocated 增长，做好换盘预案。

## 小结

排查三件套：dmesg 找内核报错定位设备，smartctl 读体检报告盯坏扇区增长，fsck/xfs_repair 修文件系统。SMART 的 Reallocated 和 Pending 扇区是最诚实的死亡预告。硬件异常没解决前别急着修上层，先备份再动刀。下一篇讲性能层面的测试与监控。
